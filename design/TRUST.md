# Trust model

What a user has to believe for a checked Locus program to mean what its specification says. This page grows only through accepted RFCs.

## Trusted components

Parts of the implementation, Locus's or another project's, whose bugs could make a false claim pass.

| ID | Component | What it must get right | Why it is trusted | What would detect a violation | Added by |
|---|---|---|---|---|---|
| `trusted.rustc.types` | rustc's type checker and trait resolution | The types of runtime values and places, and the items that names and method calls resolve to. And, through each typing skeleton, the type of every expression of logical code and of every ghost value, apart from which proposition a proof proves, and the implementation, the bound, and the associated type that each use of a trait in logical code resolves to | Locus reasons with rustc's answers rather than computing its own, so that proofs are about the program rustc compiles. It has no type checker of its own for logical code | Tests comparing the facts Locus receives with the behavior of the compiled runtime program, and litmus examples of ill-typed logical code, which must be rejected | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.rustc.borrowck` | rustc's borrow checker | Ownership in runtime code; that every place logical code reads is readable where it is read; where each mutable borrow ends, at which `final!` is resolved; and which loans flow into the lifetimes of a value given to code whose effect is unknown, from which Locus decides what that code can write | Locus has no permission checker of its own: observations are checked as borrows, and prophecies are resolved where rustc's borrows end | Litmus examples that read moved and mutably borrowed places, which must be rejected, examples about `final!`, and a `&mut` hidden in a trait object given to unverified code | [RFC 0001](rfcs/0001-compiler-pipeline.md), [RFC 0002](rfcs/0002-logical-layer.md) |
| `trusted.rustc.expansion` | rustc's macro expansion | Expanding macros, resolving names by hygiene, and evaluating each `cfg` where a macro expands, so that Locus's macros write the same typing skeleton in both programs, and carry their logical code to the driver in the checking program alone, wherever they are invoked | Build mode's two programs share one library whose macros' expansions a `cfg` selects, and Locus's macros inside other macros' input and output are expanded by rustc alone | Tests of each of Locus's macros in both programs, directly, inside other macros' input and output, and through the program's own macros | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.driver` | `locus-driver` | Reporting rustc's facts faithfully, for the program it compiled, and failing when it cannot; giving rustc each `.lc` file's lowered text at the file's own path; refusing, in every crate it compiles, verified or not, an implementation of `Model` or of the trait that carries the snapshot that neither lowering nor Locus's library wrote, and knowing lowering's by the lowered text it was given or by the identity of Locus's macro crate, never by a name; and recording, for every crate it compiles, whether the crate contains `unsafe` code, counting as such a function that foreign code can call, a static that foreign code can reach, and a naked function | It is the only path from rustc to Locus, and the only thing that sees every crate of the build, so nothing else can keep a crate from giving a type a snapshot or a model by hand | Tests comparing its reports with rustc's own output for the same program; tests of its record on crates that write no `unsafe` and have such a function or static; and tests with an implementation of `Model` written by hand in a crate that is not lowered, in a lowered crate outside Locus code, through a macro named as Locus's is, and from a crate named as Locus's is, each of which must be refused | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.facts` | The facts format | Describing types, items, resolutions, and typed bodies without losing what the logic depends on, and identifying each item by its definition rather than its path | Everything Locus knows about runtime code passes through it | Round-trip tests, and tests that each fact matches the compiled program | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.library` | Locus's library | The logical types, `Proof`, macros, stubs, and helper traits that mean what the lowering assumes. Each logical type is a zero-sized type of its own, the same in both programs, and `Proof` is one type for every proof. Each stub has the type of the logical operation it stands for, so that the type rustc gives a typing skeleton is the type of the logical code, and no stub is ever run. Each of its macros writes the same skeleton in both programs, whether lowering wrote the invocation or rustc expanded it, and in the checking program carries its logical code faithfully to the driver. `Proof` and the logical types implement exactly the traits that RFC 0002 lists. `Model` and the trait that carries the snapshot are `unsafe` traits, which the library implements only for the types whose snapshots and models it declares (`trusted.library-specs`). The types it provides in place of the standard library's collections, reference-counted pointers, cells, and locks keep the values they are given in the standard library's own types, give back the values they were given, at the types they were given them, and convert to and from the standard library's without changing what they hold. The functions of `locus::std::mem` move the values they are given and change nothing else, and a slot that is dropped without `put` aborts the process | rustc types logical code against its stubs, the driver recognizes skeletons and Locus's names by their definitions there, and Locus checks the logical code that expansions carry. The types it provides and the functions of `locus::std::mem` pass the values they are given through code that Locus does not verify, the standard library's and their own, so nothing else checks that a value which holds a proof comes back as it went in | Tests of each stub and macro against rustc, in both programs, a listing of every call that rustc resolved in each program, which must not differ, and litmus examples of Locus's macros inside other macros' input and output, including ones that read fields while others are mutably borrowed. Tests that each type it provides gives back the values it was given, and converts to the standard library's type and back without changing them. Tests of `replace`, `take_out`, and `put`: that each moves the values it is given and changes nothing else, and that a slot dropped without `put` aborts the process | [RFC 0001](rfcs/0001-compiler-pipeline.md), [RFC 0002](rfcs/0002-logical-layer.md) |
| `trusted.parser` | The parser | Where Locus syntax begins and ends | Lowering starts from its syntax trees; a misplaced boundary could check one program and run another | Byte-for-byte round trips of rustc's test suite parsed as `.lc` files | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.lowering` | Lowering, and in the first stage the `locus!` macro that does it | Writing each `.lc` file, or each `locus!` block, as the one Rust text that both programs of build mode compile: writing for each piece of logical code a typing skeleton that reads the places that code reads, where it reads them, names what it names, has its type, and is never run; writing each logic function's stub with the function's own signature, and a trait's or a type's under its reserved name; writing, where a type is declared, its snapshot type and its one implementation of `Model` and of the trait that carries the snapshot, from the declaration and from the model declared there; rejecting a source that writes a reserved name; deciding before rustc only what the source shows; pointing each module declaration at its `.lc` file; and otherwise copying the source | rustc can only check what the lowered text shows it, and Locus takes the type that rustc gives a skeleton to be the type of the logical code | Tests of lowering, including litmus examples that must be rejected; the driver's confirmation of every assumption lowering made; and the logical pass, which elaborates the logical code itself with the types rustc gave, and fails where they do not fit | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.ghost-checks` | The logical pass's ghost checks | That every proof has the proposition its position requires; which types are sealed, and that no value whose type exposes logical data reaches code that Locus does not verify, as an argument, a type argument, or a capture, checked for each instantiation of generic code, and that no value of such a type is converted to a trait object, apart from a loan: a shared reference to a value whose logical data all lies in the structural part of its snapshot, given to a function whose result and other parameters expose none, or made a shared reference to a trait object; which functions of a crate are verified and which unverified, from their signatures, their marks, their `unsafe` code, and the raw pointers they handle, and that a function that must be verified contains no `unsafe` code; and that an unverified function holds no logical code and handles no value whose type holds a logical type, at any depth through type arguments and fields; that each verified function's summary covers every place it may write, and that a place lent mutably to code whose effect is unknown has an unknown value when the borrow ends; that no proposition under interior mutability, in the type of a field or of a tuple component, reads another field or component; that two types holding logical values are taken to be the same only when their propositions are the same; that `final!` appears only in a signature's result; that a function that calls into a crate that is not taken to be sound is unverified; that no function or closure whose signature exposes logical data is coerced to a pointer, made a trait object, or passed to generic code other than the program's own verified code; that no union field holds a logical type, and no static that code outside the program can write holds logical data; that no type that holds logical data appears in the signature of a function that foreign code can call, or in a function pointer type whose ABI is not Rust's; that no runtime decision depends on a logical value; that every construction of a type with proof fields proves them, that no field its proofs read is assigned or initialized again in place, and that no proof field or field its proofs read is mutably borrowed; that a slot stays a local variable, used only as the receiver of `put`, and is passed to `put` on every path that leaves its scope; and, in export mode, that what other crates can reach states no contracts, has no logical values in its types, and reaches no field that an invariant reads, and that ghost code is written where erasure can remove it | Markers carry no propositions, so nothing else checks them | Litmus examples that pass a proof through unverified generic code, branch on a logical value, build a value without its invariant, or export a contract, which must be rejected | [RFC 0001](rfcs/0001-compiler-pipeline.md), [RFC 0002](rfcs/0002-logical-layer.md) |
| `trusted.library-specs` | The snapshots and models in Locus's library | That the snapshots it declares for standard types built on raw pointers, such as `Vec<T>`'s as a `Seq` of its elements, hold exactly what those types own, and that the models it declares for standard types describe what their values are. It states nothing about what a standard function does: a contract is in the signature of a function of Locus's library, and what that function cannot prove it assumes (`assumed.stated`) | They describe types that use `unsafe` internally, which Locus does not verify | Tests comparing each snapshot and model with the standard library's behavior | [RFC 0002](rfcs/0002-logical-layer.md) |
| `trusted.obligations` | Obligation generation | Turning each claim, and the typed bodies it is about, into the obligations the kernel checks. This includes the rules that give the context its facts: the value of each understood operation and the condition under which it returns, in a debug and in a release build, and what a write, a join, a loop, and the end of a borrow leave known. A proof is checked against those facts, so a wrong one makes a false proposition provable; and, where the kernel does not check them itself, that logic functions are total and logical types strictly positive | The kernel checks only the obligations it is given | Litmus examples that must be rejected; tests of each rule that gives a fact against rustc, in a debug and a release build, once a compiler runs them; how much of this is trusted is decided by [runtime-semantics](../issues/runtime-semantics.md) | [RFC 0001](rfcs/0001-compiler-pipeline.md), [RFC 0004](rfcs/0004-runtime-code.md), [RFC 0005](rfcs/0005-core-terms.md) |
| `trusted.validation` | Translation validation | That the program Locus builds or exports has the items and typed bodies of the program it checked, apart from Locus's macros and ghost parts. It compares every item's description, its signature, ABI, symbol, linkage, including the symbol and library a foreign item binds to, visibility, layout, target features, and impls, and every body, not only those the logic used. In build mode this compares the two compiles of the lowered text; in export mode, the exported program with the checking program | It is what makes a macro that sees different input, a macro that reads a changed file, or a bug in erasure an error rather than a program other than the one proven | Litmus examples with token-sensitive and file-reading macros, and tests that feed it deliberately wrong output, which must fail | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.export` | Export | The parts of an exported program that validation does not compare: a guard that refuses every unchecked configuration, testing every `cfg` name in the crate's sources, and `pub(crate)` for every `pub(locus)` | Rust users build the exported program without Locus | Building an exported program in unchecked configurations, which must fail, and compiling Rust crates against it that try to reach what it hides, which must fail | [RFC 0001](rfcs/0001-compiler-pipeline.md), [RFC 0002](rfcs/0002-logical-layer.md) |
| `trusted.kernel` | The kernel | Accepting a proof only if it proves its proposition in Lean's logic | Every claim rests on it; search, solvers, and AI only propose proofs | Defined by the kernel RFC, with its own tests and, where possible, an independent second checker | [RFC 0002](rfcs/0002-logical-layer.md) |
| `trusted.orchestration` | The `locus` orchestration | Pairing facts with the program they describe; in build mode, checking every crate that depends on a Locus crate, procedural macro crates included, refusing the doctests it cannot check and any other configured compiler wrapper, building each verified crate only from its checked text, and never letting an artifact built without a check stand for one; in export mode, checking every declared configuration; stopping when rustc rejects the checking program; listing every input of a verified crate, its `.lc` files and its dependencies' interfaces included, in the dep-info Cargo reads; identifying itself in what Cargo fingerprints, so that Cargo never reuses an artifact built without Locus; and recording in each result's manifest what it relied on | It decides what a successful check means, and which crates it covers | Tests that stale or mismatched facts, failing configurations, artifacts built without Locus, and dependents left unchecked fail the check | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.cargo` | Cargo | Running the wrapper for every crate in the build, and building a crate again whenever the wrapper's `rustc -vV` output or a file its dep-info lists changes | Build mode's promise that no artifact built without the check stands for a checked one rests on Cargo's fingerprints, which Locus does not control | Tests that stale artifacts and edits to `.lc` files, interfaces, and the driver are rebuilt, run against each Cargo release that Locus supports, as the Cargo-graph spike did | [RFC 0001](rfcs/0001-compiler-pipeline.md) |

## Assumptions

Facts taken without proof: axioms, specifications of external code, and properties of the platform and the build.

| ID | Assumption | Why it is needed | What would narrow it | Added by |
|---|---|---|---|---|
| `assumed.export.compiler` | The compiler that builds an exported program resolves names and types as the pinned rustc did | Rust users build an exported program with a release of their choice, which may differ from the one that checked it. In build mode, the pinned rustc builds it | Following stable releases closely; fully qualified paths where resolution could change ([distribution-and-export](../issues/distribution-and-export.md)) | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `assumed.export.dependencies` | An exported crate's dependencies resolve to versions, and are built with features, that behave as the checked ones did, for everything the logic relies on | An exported crate is checked against one resolution of its dependencies, and Cargo's feature unification can enable dependency features downstream that no guard in the crate can test. In build mode, the dependencies checked are the ones built | Exact versions for Locus dependencies, and recording dependency features ([distribution-and-export](../issues/distribution-and-export.md), [cfg-corner-cases](../issues/cfg-corner-cases.md)) | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `assumed.export.macro-inputs` | Macros in an exported program that read the environment or files (`env!`, `include!`, procedural macros) produce the same code when Rust users build it as when Locus validated it | Rust users build the exported program in their own environment, which no guard can test. In build mode, validation compares the program built with the program checked | Recording the inputs a check saw ([distribution-and-export](../issues/distribution-and-export.md)) | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `assumed.export.files` | An exported package's `.rs` files are the ones Locus exported from its sources | Rust users build the exported `.rs` files, not the `.lc` sources, and an exported file can be edited after it was checked | `cargo locus export --check` in the publisher's CI, and a command that checks a downloaded package against its sources ([distribution-and-export](../issues/distribution-and-export.md)) | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `assumed.unsafe.invariants` | `unsafe` code keeps every value of a type with proof fields satisfying them, wherever code that Locus verifies can observe the value, including in callbacks, drops, and unwinding: in the program, in its dependencies, and, for an exported crate, in the crates that use it. This is an obligation Locus adds to Rust's own, which is about undefined behavior | Locus relies on every value of such a type satisfying its proof fields, and does not check `unsafe` code. A value that breaks its invariant, such as an `Interval` with `lo > hi`, can be valid Rust: `transmute::<[u32; 2], Interval>([5, 1])` is not undefined behavior. A Locus crate's own unverified functions cannot do this, since they handle no type with proof fields. Generic `unsafe` code that is sound for every type, such as `Vec`'s, keeps every type's invariant, because it cannot know it. A hand-written `unsafe impl` makes the promise for its type; Locus rejects the `unsafe impl`s that derives and macros generate, whose promise no one wrote. What remains is `unsafe` code that Locus does not see | Each result's manifest lists this assumption with the types whose invariants it relies on, so that audits know where to look; checking `unsafe` code with permissions, later | [RFC 0002](rfcs/0002-logical-layer.md) |
| `assumed.unsafe.sound` | The standard library, the unverified crates that the project names as trusted, and each unverified function of a Locus crate that contains `unsafe` code, a naked function among them, or calls into a crate that is not named, are sound Rust, read at the level of types: their code uses a value only as the value's Rust type allows, and only while it owns the value or holds the borrow it was given. So it causes no undefined behavior for any arguments its signature admits, does not write through a shared reference outside an `UnsafeCell`, keeps no access to a place after a borrow of it ends, and keeps none to a value it has given away. Safe code needs no such assumption, since rustc enforces this there: a crate with no `unsafe` code, and none beneath it, is not on the list, and neither is an unverified function with no `unsafe` code that calls only code that is. A crate that has a function that foreign code can call (`logic.boundary.foreign`), a static that foreign code can reach (`logic.code.statics`), or a naked function counts as a crate with `unsafe` code, whether or not it writes `unsafe`: rustc checks such a function for callers that are Rust, and foreign code is not one | Every fact that survives a call rests on it. Rust's aliasing rules alone do not give it: for them a `&Vec<T>` does not freeze the vector's buffer, so only the library's own contract keeps a callee from writing it, and a value that unverified code returns could still be reached through a pointer that code kept. It is what Rust asks of every safe function, so it is a promise the code's authors have already made. Vision commitment 9 states this assumption | The project's list of trusted crates is what an audit reads; a function that calls into a crate with `unsafe` code that is not on it is unverified, and is listed itself. Each result's manifest names the listed crates it relied on, and each unverified function with `unsafe` code, and each `unsafe impl`, of a Locus crate that it passes through. Further: running that code's tests under Miri; contracts at the boundary ([boundary-contracts](../issues/boundary-contracts.md)); checking `unsafe` code with permissions, later | [RFC 0002](rfcs/0002-logical-layer.md) |
| `assumed.foreign` | Foreign code, which is code not compiled from Rust that the program calls or that calls the program, the assembly of a `global_asm!` included, keeps to the signatures the program declares for it. It gives a function of the program only valid values of that function's parameter types, and a foreign function returns a valid value of its declared result. Beyond that it does nothing that a sound Rust function of the same signature could not: it uses a value only as the value's type allows and only while it holds it, as `assumed.unsafe.sound` asks of `unsafe` Rust, and it keeps the invariant of a sealed value that a crate Locus does not verify hands it, as `assumed.unsafe.invariants` asks | Nothing on either side checks a declaration against the code behind it, and foreign code reads and writes memory as bytes. A Locus crate shows it no type that holds logical data (`logic.boundary.foreign`), so there it has no proof to forge and no value with an invariant to break. It could still pass a value that is invalid at its plain type, such as a `bool` of 2 or a dangling reference, write memory it was not given, or call a function of the program while a borrow that excludes the call is live. A function that foreign code can call need have no `unsafe` code in its body, and a foreign function declared `safe` is called with none, so what a result lists for `assumed.unsafe.sound` does not show them | Each result's manifest lists the functions of the build that foreign code can call, those that a `sym` operand names among them, and the foreign functions declared `safe` that verified code calls. A call of any other foreign function is inside an unverified function with `unsafe` code, which is listed already. An unverified crate that has a function that foreign code can call is recorded as a crate with `unsafe` code, so it is taken to be sound only when the project names it. Further: checking each declaration against the foreign code's own headers, as binding generators do; running the program's tests under sanitizers; contracts at the boundary ([boundary-contracts](../issues/boundary-contracts.md)) | [RFC 0002](rfcs/0002-logical-layer.md) |
| `assumed.stated` | Every proposition that a program, its dependencies, or Locus's library states with `unsafe assume!` holds | A program takes such a proposition on trust, and Locus checks nothing about it. Locus's library states the contracts of the types it provides around the standard library's this way, until those types are verified | A function's result lists the assumptions in its own proof and in the functions it calls, and the program's result lists every assumption in every crate it links, each with its proposition and its place; a crate can forbid assumptions in its own code with the lint `locus::assumptions`; tests that compare each assumption in Locus's library with the standard library's behavior | [RFC 0002](rfcs/0002-logical-layer.md) |
| `assumed.platform` | The operating system, the C library, and the hardware behave as the standard library's safe interfaces assume, including the state a process shares with them: signal handling, the environment, and what runs when the process exits | Locus reasons about values, and holds no fact about state that a program shares with the system beneath it. The standard library's `unsafe` code relies on that system, and soundness bugs at this boundary have been found in it and reached from safe code ("Memory Safety Bugs in Rust Standard Library", Microsoft FORGE Lab, 2026) | Nothing in Locus; fixes in the standard library, and tools that check its code against the system it runs on | [RFC 0002](rfcs/0002-logical-layer.md) |
| `assumed.lean` | Lean's logic, with its standard axioms, is consistent | Every proof is checked in Lean 4's type theory, with propositional extensionality, quotients, and classical choice | Nothing in Locus; Lean's metatheory, and long use | [RFC 0002](rfcs/0002-logical-layer.md) |
| `assumed.rustc.codegen` | rustc compiles the runtime program as Rust specifies | The runtime program is ordinary Rust | Nothing in Locus; this is the trust every Rust program places in its compiler | [RFC 0001](rfcs/0001-compiler-pipeline.md) |

## Rules

- Every entry has a permanent ID in the first column of its table: `trusted.<name>` for a component, `assumed.<name>` for an assumption, in dotted kebab-case. Like a rule ID, it never changes, and it is never reused once an entry is removed.
- Every entry names the accepted RFC that added it.
- Every entry says what it covers, why it is needed, and what would detect a violation or narrow it.
- A change that adds to this page, or depends on something not listed here, is a design change and needs an RFC.
