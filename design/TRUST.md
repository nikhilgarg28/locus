# Trust model

What a user has to believe for a checked Locus program to mean what its specification says. This page grows only through accepted RFCs.

## Trusted components

Parts of the implementation, Locus's or another project's, whose bugs could make a false claim pass.

| ID | Component | What it must get right | Why it is trusted | What would detect a violation | Added by |
|---|---|---|---|---|---|
| `trusted.rustc.types` | rustc's type checker and trait resolution | The types of runtime values and places, and the items that names and method calls resolve to | Locus reasons with rustc's answers rather than computing its own, so that proofs are about the program rustc compiles | Tests comparing the facts Locus receives with the behavior of the compiled runtime program | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.rustc.borrowck` | rustc's borrow checker | Ownership in runtime code; that every place logical code reads is readable where it is read; and where each mutable borrow ends, at which `final!` is resolved | Locus has no permission checker of its own: observations are checked as borrows, and prophecies are resolved where rustc's borrows end | Litmus examples that read moved and mutably borrowed places, which must be rejected, and examples about `final!` | [RFC 0001](rfcs/0001-compiler-pipeline.md), [RFC 0002](rfcs/0002-logical-layer.md) |
| `trusted.driver` | `locus-driver` | Reporting rustc's facts faithfully, for the program it compiled, and failing when it cannot | It is the only path from rustc to Locus | Tests comparing its reports with rustc's own output for the same program | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.facts` | The facts format | Describing types, items, resolutions, and typed bodies without losing what the logic depends on, and identifying each item by its definition rather than its path | Everything Locus knows about runtime code passes through it | Round-trip tests, and tests that each fact matches the compiled program | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.library` | Locus's library | Markers, macros, probes, and stubs that mean what the lowering assumes. In the checking program, each of its macros observes every place its logical code reads and carries that code faithfully to the driver, whether lowering wrote the invocation or rustc expanded it; in the runtime program, each expands to its marker and nothing else. `Erased` and `ErasedData` implement exactly the traits that RFC 0002 lists | The driver recognizes probes and Locus's names by their definitions there, and Locus checks the logical code that expansions carry | Tests of each probe and macro against rustc, in both programs, and litmus examples of Locus's macros inside other macros' input and output, including ones that read fields while others are mutably borrowed | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.parser` | The parser | Where Locus syntax begins and ends | Lowering starts from its syntax trees; a misplaced boundary could check one program and run another | Byte-for-byte round trips of rustc's test suite parsed as `.lc` files | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.lowering` | Lowering | Writing each `.lc` file as the one Rust text that both programs of build mode compile: observing every place logical code reads, where it reads it; probing every name it uses; deciding before rustc only what the source shows; recording which bindings are ghost, so that expansions rustc performs observe the right places; and otherwise copying the source | rustc can only check what the lowered text shows it | Tests of lowering, including litmus examples that must be rejected, and the driver's confirmation of every assumption lowering made | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.ghost-checks` | The logical pass's ghost checks | That every proof has the proposition its position requires; that ghost contents are forgotten when they pass through code Locus neither checks nor has a specification for, or through a raw pointer, a cast, or `transmute`; that no way to write a place holding logical values that are not completable reaches such code, judged conservatively from the value's type and type arguments and the library's list of types writable through a shared handle; that no function needing a proof is coerced to a pointer, made a trait object, or passed to generic code other than the program's own; that no runtime decision depends on a logical value; that every construction of a type with proof fields, and every assignment to a field its proofs read, proves them, and that no proof field or field its proofs read is mutably borrowed; and, in export mode, that what other crates can reach states no contracts, has no logical values in its types, and reaches no field that an invariant reads, and that ghost code is written where erasure can remove it | Markers carry no propositions, so nothing else checks them | Litmus examples that pass a proof through unspecified generic code, branch on a logical value, build a value without its invariant, or export a contract, which must be rejected | [RFC 0001](rfcs/0001-compiler-pipeline.md), [RFC 0002](rfcs/0002-logical-layer.md) |
| `trusted.library-specs` | The snapshots, models, and specifications in Locus's library | That the snapshots it declares for standard types built on raw pointers, such as `Vec<T>`'s as a `Seq` of its elements, hold exactly what those types own; that the models it declares, and the specifications of standard functions, including what generic code such as `Vec::push` does with the values it holds, describe what those types and functions do; that the methods of `Cell`, `RefCell`, and `Mutex` keep the types of their contents; that its list of types writable through a shared handle, channels' senders included, is complete; and that the logical types it declares completable are | They describe code that uses `unsafe` internally, which Locus does not verify | Tests comparing each model and specification with the standard library's behavior | [RFC 0002](rfcs/0002-logical-layer.md) |
| `trusted.obligations` | Obligation generation | Turning each claim, and the typed bodies it is about, into the obligations the kernel checks | The kernel checks only the obligations it is given | Litmus examples that must be rejected; how much of this is trusted is decided by [#6](https://github.com/nikhilgarg28/locus/issues/6) | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.validation` | Translation validation | That the program Locus builds or exports has the items and typed bodies of the program it checked, apart from Locus's macros and ghost parts. In build mode this compares the two compiles of the lowered text; in export mode, the exported program with the checking program | It is what makes a macro that sees different input, a macro that reads a changed file, or a bug in erasure an error rather than a program other than the one proven | Litmus examples with token-sensitive and file-reading macros, and tests that feed it deliberately wrong output, which must fail | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `trusted.export` | Export | The parts of an exported program that validation does not compare: a guard that refuses every unchecked configuration, and `pub(crate)` for every `pub(locus)` | Rust users build the exported program without Locus | Building an exported program in unchecked configurations, which must fail, and compiling Rust crates against it that try to reach what it hides, which must fail | [RFC 0001](rfcs/0001-compiler-pipeline.md), [RFC 0002](rfcs/0002-logical-layer.md) |
| `trusted.kernel` | The kernel | Accepting a proof only if it proves its proposition in Lean's logic | Every claim rests on it; search, solvers, and AI only propose proofs | Defined by the kernel RFC, with its own tests and, where possible, an independent second checker | [RFC 0002](rfcs/0002-logical-layer.md) |
| `trusted.orchestration` | The `locus` orchestration | Pairing facts with the program they describe; in build mode, checking every crate that depends on a Locus crate, building each checked crate only from its checked text, and never letting an artifact built without a check stand for one; in export mode, checking every declared configuration; stopping when rustc rejects the checking program; listing every input of a checked crate, its `.lc` files and its dependencies' interfaces included, in the dep-info Cargo reads; identifying itself in what Cargo fingerprints, so that Cargo never reuses an artifact built without Locus; and recording in each result's manifest what it relied on | It decides what a successful check means, and which crates it covers | Tests that stale or mismatched facts, failing configurations, artifacts built without Locus, and dependents left unchecked fail the check | [RFC 0001](rfcs/0001-compiler-pipeline.md) |

## Assumptions

Facts taken without proof: axioms, specifications of external code, and properties of the platform and the build.

| ID | Assumption | Why it is needed | What would narrow it | Added by |
|---|---|---|---|---|
| `assumed.export.compiler` | The compiler that builds an exported program resolves names and types as the pinned rustc did | Rust users build an exported program with a release of their choice, which may differ from the one that checked it. In build mode, the pinned rustc builds it | Following stable releases closely; fully qualified paths where resolution could change ([#7](https://github.com/nikhilgarg28/locus/issues/7)) | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `assumed.export.dependencies` | An exported crate's dependencies resolve to versions, and are built with features, that behave as the checked ones did, for everything the logic relies on | An exported crate is checked against one resolution of its dependencies, and Cargo's feature unification can enable dependency features downstream that no guard in the crate can test. In build mode, the dependencies checked are the ones built | Exact versions for Locus dependencies, and recording dependency features ([#7](https://github.com/nikhilgarg28/locus/issues/7), [#9](https://github.com/nikhilgarg28/locus/issues/9)) | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `assumed.export.macro-inputs` | Macros in an exported program that read the environment or files (`env!`, `include!`, procedural macros) produce the same code when Rust users build it as when Locus validated it | Rust users build the exported program in their own environment, which no guard can test. In build mode, validation compares the program built with the program checked | Recording the inputs a check saw ([#7](https://github.com/nikhilgarg28/locus/issues/7)) | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `assumed.export.files` | An exported package's `.rs` files are the ones Locus exported from its sources | Rust users build the exported `.rs` files, not the `.lc` sources, and an exported file can be edited after it was checked | `cargo locus export --check` in the publisher's CI, and a command that checks a downloaded package against its sources ([#7](https://github.com/nikhilgarg28/locus/issues/7)) | [RFC 0001](rfcs/0001-compiler-pipeline.md) |
| `assumed.unsafe.invariants` | `unsafe` code, in the crate and in its dependencies, never creates or changes a value of a type with proof fields except through code that Locus checks | Locus relies on every value of such a type satisfying its proof fields. This is a promise beyond Rust's safety contract: after erasure, a value that breaks its invariant, such as an `Interval` with `lo > hi`, can be valid Rust, so `mem::zeroed`, `transmute`, or a raw write can break it without breaking any rule of Rust's. A hand-written `unsafe impl` on such a type makes this promise for it; Locus rejects the `unsafe impl`s that derives and macros generate, whose promise no one wrote | Each result's manifest lists this assumption when it relies on the invariant of a type that `unsafe` code can reach, so that audits know where to look; checking `unsafe` code, later | [RFC 0002](rfcs/0002-logical-layer.md) |
| `assumed.lean` | Lean's logic, with its standard axioms, is consistent | Every proof is checked in Lean 4's type theory, with propositional extensionality, quotients, and classical choice | Nothing in Locus; Lean's metatheory, and long use | [RFC 0002](rfcs/0002-logical-layer.md) |
| `assumed.rustc.codegen` | rustc compiles the runtime program as Rust specifies | The runtime program is ordinary Rust | Nothing in Locus; this is the trust every Rust program places in its compiler | [RFC 0001](rfcs/0001-compiler-pipeline.md) |

## Rules

- Every entry has a permanent ID in the first column of its table: `trusted.<name>` for a component, `assumed.<name>` for an assumption, in dotted kebab-case. Like a rule ID, it never changes, and it is never reused once an entry is removed.
- Every entry names the accepted RFC that added it.
- Every entry says what it covers, why it is needed, and what would detect a violation or narrow it.
- A change that adds to this page, or depends on something not listed here, is a design change and needs an RFC.
