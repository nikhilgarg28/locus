# Initial core implementation plan

This plan refines milestone 0 in the design brief. The compiler is written in Rust with a handwritten lexer and recursive-descent/Pratt parser. We reuse `annotate-snippets` for presentation; Locus owns its diagnostic model. Self-hosting and verification of compiler components are later projects.

The target is the fragment in [the core language specification](core-language-spec.md): `u8` with explicit wrapping operations, `bool`, unit, immutable bindings, tuples, named structs, nonrecursive enums and `match`, nonrecursive `fn` and `math fn` declarations, state-passing loops in `fn`, bounded iteration, propositions, `prop` declarations, and proofs checked by the Locus kernel. Mathematical `Int`/`Nat`, arithmetic operators, generics, recursion, closures, mutation, ownership, termination measures, contracts, trusted declarations, and native code generation remain later milestones. [rust-features.md](rust-features.md) is the running list of Rust features outside the core.

| Batch | Scope | Completion check |
|---|---|---|
| 0.1 | Specify surface grammar, scope rules, and the logical encoding. Spike the proof kernel before proof elaboration, working from hand-written kernel terms. | Kernel gates K1 to K6 below pass, in order. |
| 0.2 | Rust project, source locations, structured diagnostics, handwritten lexer, CLI. | Exact literal text survives lexing; comments, invalid characters, and EOF receive useful diagnostics. |
| 0.3 | Source-located AST, recursive-descent parser, Pratt expression parser, recovery. | Parse core examples; distinguish precedence, grouping, function modes, proof forms, and named result fields; continue after independent syntax errors. |
| 0.3b | Frontend realignment with the specification: `math fn` replacing `def`; `struct`, `enum`, and `prop` declarations; `Enum::Variant` paths; `match`; positional projection; `loop`/`break`/`continue(...)`; bounded `for`; function types; literal patterns. Retire `@{ ... }` proof blocks, `Nat`, and `+`. Done. |
| 0.4 | Name resolution and scopes. | Bindings have distinct IDs; undefined names, escaped result binders, arm-local and loop-local escapes, and any declaration cycle among functions, enums, and props are rejected. |
| 0.5 | Ordinary typing and reference execution for `u8`, `bool`, tuples, structs, enums, `match`, `if`, loops, and bounded `for`. | Proof-free functions execute; ill-typed programs, non-exhaustive matches, and loops inside `math fn` fail before execution. |
| 0.6 | Kernel: term language; comparison up to renaming and proof irrelevance with no normalizer; computation as explicit equality axioms that the elaborator inserts; equality at every data type and `Prop`, without extensionality; excluded middle; internal `Forall` and `Implies` (needed as soon as facts in scope become hypotheses), internal `Nat` with its recursor, the `u8` model and native evaluation, defining equations with `unfold`/`fold`/`rewrite`. Proof types `@claim` / `@[condition]`, the hole's first tier (facts in scope, reflexivity, closed evaluation), ghost flow and math-totality checks. | Valid equality proofs pass; false or unsolved claims fail. A proof hole needs an expected proposition; `_` never admits an unchecked claim. Reject ghost data flowing into execution. Export accepted terms and recheck a sample with an independent checker. |
| 0.7 | Proof arguments, local proofs, lemma calls, declarative proof style, kernel-level prelude: schematic equality lemmas and `u8` ordering lemmas proved over the `Nat` model. | Compose equalities through stated intermediate facts and lemma calls; reject mismatched evidence, including evidence that merely implies the expected proposition. |
| 0.8 | Dependent data/proof tuples, structs, and variant payloads; destructuring. | Returned data instantiates later proof fields and callers can reuse that evidence. |
| 0.9 | The three-kinded context with upgrade for ghost rules; facts from `match` arms, with `if` as `match` on `bool`; per-path statements for proofs inside `fn` bodies, built from the internal `Forall` and `Implies` of 0.6; the distinction between a ghost result and an erasable computation. | Check every arm symbolically; prevent arm assumptions from escaping unjustifiably; a divergent `fn` returning `@[false]` proves nothing in logic; a pattern that inspects a ghost field to choose a runtime arm is rejected. |
| 0.10 | Surface `forall`, `=>`, `exists`; `prop` declarations and the prelude `True`, `False`, `And`, `Or`; match on proofs; applying quantified proofs; math function names as proofs. Hole tiers for propositional reasoning, congruence, and unfolding. | Introduce and consume each logical form; reject a match on a proof that produces non-proof data or whose arms are not total, a `prop` variant concluding another proposition, runtime branching on propositions, and implicit Bool/Prop coercions. |
| 0.11 | Loop state proofs; bounded `for` checked by the term-level range-iteration rule, with index-dependent state that erases to a fixed state type. | Prove the bounded walk and bounded count examples; cover an empty range, rejected reversed bounds, `hi == 255`, and nested iteration; reject a `continue` that fails to re-establish state evidence. Model 255 wrapping to 0 and reject unconditional monotonicity. |
| 0.12 | Erasure as a compositional function on types and terms; integrated core release. | Execute proof-bearing programs without runtime proposition or proof objects, preserving data results, evaluation order, and divergence; erased terms are well typed at the erased type; no trap is reachable in the test programs. |

Diagnostics are part of each batch: preserve requirement origins, report Locus-level goals, distinguish failed search from refutation, test errors and any machine-applicable fixes. Recovery nodes support diagnostics only; any error prevents successful compilation.

## What this milestone is for, and how it will be judged

The central promise is that someone can write familiar code, state meaningful facts about it, and get understandable help establishing them. The kernel is a foundation for that; the experience from source to executable is what decides whether the language succeeds. Until that has been tested, the core feature set holds steady.

**The test.** One polished end-to-end example: source code for a small bounded state machine; a result that carries evidence; a caller that reuses that evidence; useful diagnostics for an intentional mistake; and matching interpreted and generated behavior. Everything between here and there serves that example.

**Boundaries to protect.**

- Dependency is restricted to propositions. A value may change what a later proof field asserts and never the runtime layout. Dependent results, validated data, and loop invariants all rest on this one mechanism. A new feature must earn its place inside the boundary before the type system is widened.
- Loop invariants are evidence in loop state: initialization supplies it, and each iteration supplies it again.
- Ghost data is part of the logical value, so two logical values can share a runtime representation. That is kept, and it will resurface in equality, serialization, mutation, and foreign interfaces. Each future expansion of ghost data must come with a concrete use case.
- This milestone is a language for verified immutable computation. Ownership, aliasing, destruction, and mutation raise questions it cannot answer, above all which state a proof describes after another reference changes storage. Before promising broad Rust compatibility, test the extension with one narrow borrowing-and-mutation example.

**Acceptance criteria for the proof-writing experience.** The hand-built proofs so far show that the rules compose, not that the `let`-based surface is pleasant. Removing normalization from the kernel moved work into elaboration: projection, substitution, unfolding, and equality transport still have to happen somewhere, and if users must repair them by hand, friendly syntax will not save the experience.

- Routine rearrangements, such as introducing a local variable, destructuring a tuple, or extracting a helper, require little or no proof repair when the interfaces involved stay equivalent.
- An unsolved `_` shows the expected claim, the useful facts available, and the remaining gap.

Both are to be exercised by the first integrated examples, not deferred to a tooling milestone.

**Measure before large proofs are normal.** Predictable checking is not the same as fast compilation, and making every computation step explicit can produce a great deal of evidence. Track separately: time spent constructing proofs; the size of the resulting proof terms; time and memory spent checking them; and the cost of rechecking after a small edit. Checked lemma reuse and stable interfaces will matter early. Do not optimize the representation before there are numbers.

**Preferences, not constraints.**

- Generated Rust resembling the source is a strong preference. Temporary bindings and modest structural changes are acceptable where they make evaluation order or the correctness of erasure simpler.
- `Proved` and `Ghost` are internal representations. They do not dictate the eventual public Rust interface.
- The typed tree's two branches keep the output readable at a real cost in trust: a sound kernel cannot establish that the checked program and the executed program agree. Differential testing of the two branches is the next step for exactly that reason.

## Order of work

The batch table above groups the work by topic. The order in which it is done is different: the kernel comes first, from hand-written terms, and the frontend is realigned last, against a kernel interface that has already survived the hard examples. The next milestone is a working, deliberately small checker, not a larger specification.

1. **Kernel contract and kernel, together.** Work from hand-written kernel terms, independent of the parser. For each rule, write its exact premises and conclusion in [kernel-contract.md](kernel-contract.md) as the rule is implemented. This is the kernel part of batches 0.1 and 0.6.
2. **Difficult boundaries early.** The gates below include the cases most likely to force a change of representation.
3. **The intermediate representations.** [ir-architecture.md](ir-architecture.md) describes them. A source-shaped *typed tree* is the one shared artifact. A trusted `lower` produces the *check IR*, let-normal executable code over kernel terms, which the trusted exec checker walks while maintaining a kernel context. A trusted `erase` projects the typed tree to an *erased tree*, which the reference interpreter runs and from which Rust is printed, so that the generated Rust reads like the source. Ghost positions become the zero-sized markers `Proved` and `Ghost`, so erasure preserves shape. Build the check IR and the exec checker first, from hand-built programs; then the typed tree, `lower`, and `erase`; then the interpreter.
4. **Erasure and divergence tests, then the frontend.** An interpreter for the check IR that skips ghosts must agree with the interpreter for the erased tree on every program, including on running out of fuel. Batches 0.3b and 0.4 then connect the parser and name resolution to the interfaces that exist by then. Surface elaboration, holes, and the prelude (batches 0.7 to 0.11) follow.

The kernel spike is split into acceptance gates. Each gate is small, and a later gate is not started until the earlier ones pass.

| Gate | Scope | Passes when |
|---|---|---|
| K1 (done) | Terms, contexts with the three kinds of entry and upgrade, comparison up to renaming and proof irrelevance, `Eq` with reflexivity and transport, internal `Forall` and `Implies`. | A true equality checks; a false one is rejected; a fact in scope discharges an identical goal; a ghost variable is rejected in an executable term. |
| K2 (done) | Tuples, structs, dependent proof fields, and the `let`, projection, and literal computation axioms. | A dependent data/proof result checks; returned data instantiates a later proof field; two `NonZero` values with equal bytes are equal without a proof step. |
| K3 (done) | Math functions, defining equations, `unfold`/`fold`/`rewrite`, function values, `Prop` as a value. | An explicit unfolding step checks; `select() == successor` is provable at a function type while pointwise agreement does not prove function equality; `Claim { proposition: [true] }` and `Claim { proposition: [false] }` are distinguishable and their projections compute. |
| K4 (done) | Enums and the case rule with arm evidence; declared props, the index-equation case rule, `Exists`, excluded middle with dependency recording. | An indexed proposition match supplies its index equation; a match on a proof with a non-proof result or a non-total arm is rejected; a variant concluding another proposition is rejected; constructor disjointness is derived. |
| K5 (done) | Internal `Nat` with induction; the `u8` model, reflection lemmas, and native evaluation. | A `u8` ordering lemma over three variables is proved from the model, not by enumeration; native evaluation agrees with the model exhaustively for one-byte operations. |
| K6 (done) | The range-iteration rule. | The bounded-count example checks with index-dependent state; empty range, rejected reversed bounds, `hi == 255`, and nested iteration are covered. |

Separately from the kernel gates, the interpreter must show that a divergent proof-returning call survives erasure, including when it appears as an argument and as a field of a proof constructor.

## Proof kernel decision

Locus uses its own proof kernel, written in Rust. A Lean-backed adapter is no longer the plan. The decision rests on these commitments:

- The logic is classical. The planned soundness argument is a denotational model in the style of explicit refinement types (Ghalayini and Krishnaswami, ICFP 2023): propositions denote truth values, and types denote sets of logical values related to runtime representations. Locus keeps the two apart because ghost data such as a `Prop` field belongs to the logical value but not to the representation; for types without ghost data this reduces to the paper's subset reading. Its mechanized Lean 4 development is a starting point; the two-layer values, divergence, and declared propositions are the parts Locus must add. Excluded middle is a single named lemma whose uses are recorded. Until the model is checked against every kernel rule, consistency is a goal. Exporting accepted terms to an independent implementation tests the kernel but does not replace that argument.
- The kernel has no conversion checker. It compares terms up to renaming and proof irrelevance; every computation step is an explicit equality axiom used through transport. The elaborator inserts the steps for immutable lets, projections, matches on known constructors, and literal arithmetic, so the programmer still sees the minimal type identity of the specification. Function bodies are unfolded only on request.
- Proof irrelevance holds, as part of conversion. `u8` is modelled as a natural number below 256 over a kernel-internal `Nat` with a recursor; its ordering lemmas are proved from that model. Native evaluation must agree with the model and can decide closed terms. Induction over that `Nat` is the proof-level recursion rule; bounded iteration is a separate term-level rule whose index-dependent state erases to a plain loop.
- Everything that constructs proofs is untrusted: the elaborator, the hole solver, and any later decision procedure, external solver, or model. Each must produce a kernel term, or a certificate for a checker that is explicitly added to the trusted base.
- Proofs are written declaratively, as stated intermediate facts joined by lemma calls and holes. There is no tactic language. The hole's search is fixed and bounded by step counts, never by time, and it does not search the prelude, so that its behavior is predictable; found proofs are recorded so rechecking does not repeat the search.
- The prelude is checked, not trusted. The main cost of not building on Lean is this lemma library; statements can be ported, proofs must be redone.

Regardless of kernel, the translation of programs into kernel statements, erasure, and execution initially remain trusted compiler components. Proof acceptance alone does not establish that generated machine code preserves the source semantics.

## First implementation increment

Batches 0.2 and 0.3 are implemented, together with the surface grammar portion of 0.1 as it stood before the specification was revised. The kernel spike remains pending. The CLI exposes syntax tools only: `tokens`, `parse`, and `ast`. There is no `check` command before semantic and proof checking exist.

The parser follows the specification's grammar (batch 0.3b is done): [grammar.md](grammar.md) describes it, and the retired forms `def`, `@{ ... }`, `+`, and arrays receive migration diagnostics. The files in `examples/` follow the specification. `examples/lock.loc`, a lock that tolerates three wrong codes, is the end-to-end example this milestone is judged by: a transition function whose result carries the bound on the failure count, a bounded `for` that carries the same evidence as loop state, and a caller that reuses what the loop returned. It parses; nothing after parsing handles it yet.

Acceptance programs cover ordinary functions, `increment` with a dependent result, branch-based `preserve`, separately defined proofs, local and constant propositions, logical definitions, operations on proposition values, quantified propositions, and the proposed `u8` wrapping operation. Syntax acceptance of these files does not establish their validity as programs or proofs.

Validation covers lexical errors and UTF-8 spans, precedence and associativity, grouping versus tuples, proof blocks and holes, named and inline proof types, contextual bracket syntax versus explicit arrays, dependent result syntax, recovery, applicable punctuation fixes, recursion limits, malformed-input robustness, diagnostic rendering, and CLI exit behavior. The first increment passes `cargo test --locked --offline`, `cargo fmt --check`, and `cargo clippy --locked --offline --all-targets -- -D warnings`.

The parser records executable versus logical declarations but does not yet enforce the ghost flow or totality rules. The parser retains `[e]` as a neutral bracket node. In the core `[e]` is always a proposition literal, so elaboration no longer chooses between a proposition and a singleton array. Rejecting unbracketed Boolean expressions in `Prop` positions and checking the types of logical operations remain elaboration work. Array/slice types and array literal forms are represented syntactically to keep this distinction precise; executable arrays remain a later milestone. Whether the bracket literal survives at all is an open question in the specification.

All six kernel gates, K1 to K6, are implemented in `src/kernel/`, with their rules stated in [kernel-contract.md](kernel-contract.md) and their acceptance tests in `tests/kernel.rs`, `tests/kernel_products.rs`, `tests/kernel_functions.rs`, `tests/kernel_cases.rs`, `tests/kernel_numbers.rs`, `tests/kernel_loops.rs`, `tests/kernel_evaluation.rs`, and `tests/kernel_depth.rs`. The kernel is independent of the parser and is driven by hand-written terms. Step 3 of the order of work is under way, following the build order in [ir-architecture.md](ir-architecture.md). Done: term-level `case` arms carry their fact; the check IR and the exec checker exist in `src/exec/` and accept hand-built `increment`, a caller that reuses its evidence, `preserve`, `classify` with a matching caller, `bounded_walk` with its loop invariant, a bounded `for` whose body calls an ordinary function and carries an index-dependent invariant, and the divergent `spin` with a caller, and reject the corresponding mistakes (`tests/exec_check.rs`). The typed tree and `lower` exist in `src/typed/`: the specification's programs are written in source shape in `tests/typed_lower.rs`, lowered, and accepted, including one tree lowered both as an ordinary function and as a math function, a nested call, a negated condition, a loop with its invariant, and a bounded `for` lowered both to a kernel term and to a statement. The erased tree, `erase`, its type checker, the reference interpreter with fuel, and the Rust printer exist in `src/erased/`. A ghost-skipping interpreter for the check IR (`src/exec/interp.rs`) is compared with the reference interpreter in `tests/differential.rs`: eight programs agree on every byte, both agree that the caller of a divergent function does not return, and a tampered erased module is caught. `tests/rust_output.rs` compiles the printed Rust with rustc under `-D warnings`, runs it, and compares its output with the interpreter's.

So steps 3 and 4 of the order of work are done for hand-built typed trees, and the back half of the pipeline runs end to end: typed tree, lowering and checking, erasure, interpretation, and compiled Rust. What is missing is the rest of the front half: name resolution (0.4), and the elaborator that produces typed trees from source, with holes and their diagnostics. The parser realignment (0.3b) is done. The rest is the next work, aimed at the end-to-end example described above. The gaps recorded when the gates were finished have since been closed: projection through nested dependent products, arbitrary-precision `Nat` literals, the closed-term evaluator with proof by cases over `u8`, the range successor axiom, derived forms that reach under binders, the ordering lemmas `bounded_walk` needs, and a depth bound on input. What remains is listed at the end of the kernel contract. Frontend realignment (0.3b) and name resolution (0.4: resolved binding identities, lexical scopes, result-field scope, and declaration dependency cycles) come after the kernel gates, the interpreter, and the erasure tests.
