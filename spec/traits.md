# Traits

There is one set of traits, and it is Rust's. A trait is implemented for a runtime type or for a logical type, and rustc decides which implementation each use means. This chapter says what a trait may hold beside what Rust gives it, what an implementation must match, what a bound means to code that is generic over it, which traits a logical type implements, what an operator means, and what a law trait of Locus's library is. [RFC 0006](../design/rfcs/0006-traits.md) explains the design, and [RFC 0001](../design/rfcs/0001-compiler-pipeline.md) says how rustc is given logical types and logic functions.

In this chapter a *method that runs* is a member that a trait declares with `fn`, with a default body or without one, as against a logic function, which it declares with `logic fn`. A *Locus trait* is a trait with logical content ([`traits.members`](#what-a-trait-holds)), and a *law trait* is a Locus trait of Locus's library that stands beside a trait of the standard library ([`traits.laws.provided`](#law-traits)).

## Rust's traits

r[traits.rust]
A trait, an implementation, a bound, and the implementation that a call or a path means are Rust's, for runtime types and logical types alike. rustc decides them, in logical code as in runtime code, by coherence, the orphan rule, and its own resolution, and Locus never selects another implementation or another trait. A proposition never decides which implementation applies: to rustc every proof type is the one type `Proof` ([`logic.ghost.erased`](logical-layer.md#ghost-values)).

## What a trait holds

r[traits.members]
Beside what a Rust trait holds, a trait may hold logic functions, a lemma being a logic function that returns a proof; associated types bounded by `Logical`; and logical values, proofs among them, in the parameters and results of its methods. A logic function in a trait may have a default body. A trait holds no `prop` declaration and no associated constant of a logical type, for now. A trait that holds any of these, itself, through a supertrait, or through a bound on an associated type, is a *Locus trait*.

r[traits.members.kind]
Whether a member of a trait is a logic function is part of its declaration in the trait, and every implementation gives the member as the trait declares it: an implementation that gives a `fn` where the trait says `logic fn`, or a `logic fn` where it says `fn`, is rejected. So what a bound gives generic code never depends on the implementation: logical code calls a member that the trait declares a logic function, at every type, and calls no other ([`logic.code.no-runtime-calls`](logical-layer.md#logical-code)).

r[traits.logical]
`Logical` is a trait that holds for exactly the logical types. Locus defines it: it has no member that a program can name, and no program implements it. It is a bound like any other. A type parameter of a runtime function, of a type, or of an `impl` that is bounded by `Logical` ranges over the logical types, and a value of such a parameter is a ghost value. A trait whose logic functions take or return `Self` as a value has `Logical` as a supertrait, written in its declaration. None is implied: without it `Self` may be a runtime type, which no parameter or result of a logic function has ([`logic.fn.parameters`](logical-layer.md#logical-code)).

r[traits.model-bounds]
A `Snapshot` bound may be a supertrait or a bound on a trait parameter, associated type, or method parameter. It permits capture and naming `Snap<Self>` or `Snap<T>` under the same rules as on a function. Logical types meet it with identity capture. `View` is an ordinary optional library trait whose supertrait is `Snapshot`, with associated logical type `V` and logic function `view(s: Snap<Self>) -> Self::V`. It is invoked explicitly and has no privileged capture or coherence rule. A contract implies no missing bound.

## Implementations

r[traits.impls.conform]
An implementation gives every member that has no default. With `Self`, the trait's parameters, and its associated types filled in, each member's signature in the implementation is the trait's: its parameters and its result have the same types, each logical type and each proposition among them the same ([`logic.ghost.type-identity`](logical-layer.md#ghost-values)). An implementation adds no logical value to a signature, leaves none out, and states no other contract, a stronger one included. rustc compares the two signatures with `Proof` for every proof, so Locus compares the propositions.

r[traits.impls.headers]
No proof type, no dependent tuple, and no snapshot type, `Snap<T>` or `CutSnap<T>`, is the self type of an implementation or an argument of its trait, alone or inside another type. rustc sees every proof as `Proof` and compares no proposition, and it sees a snapshot type as the type it is equal to, as `Snap<u32>` and `Snap<u64>` are both `Nat`, so such an implementation would apply more widely than its header reads. The header is judged as rustc resolved it, so an alias of such a type is rejected as the type is. Any other logical type may be written there, in an implementation of any trait for a runtime type, and in one for a logical type that [`traits.impls.logical-types`](#implementations) allows: two implementations may differ only in a logical type argument, as `impl Scale<Int> for Meters` and `impl Scale<Nat> for Meters` do. An associated type that a trait bounds by `Logical` is given any logical type, a proof type among them, by an implementation for a runtime type as for a logical one, whether or not the trait has a method that runs. An associated-type binding in a bound, as in `T: Claim<P = @False>`, may be any logical type, a proof type among them. rustc decides that such a bound holds with every proof seen as `Proof`, and Locus then compares the binding with the associated type of the implementation that rustc resolved, propositions included ([`logic.ghost.type-identity`](logical-layer.md#ghost-values)), and rejects a use where the two differ: a type argument given for a parameter with such a bound, one that meets such a `where` clause, an implementation of a trait whose supertrait has such a binding, and an implementation that rustc selects under such a bound, which then has no evidence ([`traits.evidence`](#bounds)).

r[traits.impls.logical-types]
A program writes no implementation, for a logical type, of a trait that has a method that runs, in the trait itself or in a supertrait, a method with a default body included. The logical types have only the implementations of such traits that the language gives them ([`logic.ghost.marker-traits`](logical-layer.md#ghost-values)). So a trait that a program implements for a logical type holds logic functions and associated types and nothing that runs, and a conversion or an operation on logical values is a logic function of a trait that declares it so. Which type an implementation is for, and which methods its trait has, are read after rustc has resolved them, so the rule holds through an alias, and for a trait that another module or another crate declares.

r[traits.impls.acyclic]
No logic function and no proof depends on itself, a lemma and a default body that an implementation takes included, except by the recursion that [`logic.fn.total`](logical-layer.md#logical-code) allows. One depends on each member that it calls, such as `Self::op(a, b)`, as the implementation that rustc selected there defines it, and on what that definition depends on, through code that is generic over the trait and through the evidence that such code is given. Evidence alone depends on nothing: it names the evidence it holds ([`traits.evidence`](#bounds)), so an implementation whose associated type refers back to its own type, as `type Next = Self` does under `type Next: Chain`, is accepted, and only a member that is used can close a cycle. So a logic function of an implementation does not reach itself, through generic code or through such an associated type, and unfolding a definition ends. A method that runs is not held to this: it may call itself and may never return, and a call that never returns gives its caller no proof.

## Bounds

r[traits.evidence]
In the core ([`core.elaboration`](core.md)) a bound is a parameter. The evidence that a type implements a trait is a record of: the trait's logic functions at that type; its associated types, the logical ones as logical types and the others as the runtime types that rustc resolved, with the evidence for each bound on them; the contract of each method, which is its signature with its propositions; and the evidence for each supertrait. An implementation defines the evidence, as a function of the evidence for its own bounds. The evidence for an implementation at given type arguments is a constant with a name of its own, and a record holds the evidence for a bound on an associated type, or for a supertrait, by naming it: so a record may name itself, as the evidence for `Int: Chain` does where `Chain` declares `type Next: Chain` and the implementation gives `type Next = Int`, and evidence is a finite term that names constants. Generic code takes the evidence for each of its bounds as a parameter, and a use at a type where rustc selected an implementation is given that implementation's evidence. There is evidence for an implementation only where there is evidence for each bound that it needs. A method's contract says what holds when a call of the method returns, and gives no term for its result: a method is not a logic function, and logical code does not call it.

r[traits.bounds]
In code that is generic over a bound, each member of the trait is known by the signature that the trait declares, and by nothing else. A logic function of the trait is not unfolded there, and what is known of it is what the trait's lemmas return, each where the code calls it: a hole calls no lemma ([`proofs.holes`](proofs.md#constructing-proofs)). Where rustc selected an implementation, a logic function of the trait is that implementation's, and unfolds where conversion unfolds a body like it ([`core.conversion`](core.md)). The proofs of generic code are checked once, against the evidence that it takes as a parameter, and hold at every instantiation for which there is evidence. The boundary with unverified code is still checked for each instantiation ([`logic.ghost.generic-instantiations`](logical-layer.md#ghost-values)).

r[traits.names]
A logic function of a trait is named in logical code as Rust names an associated function: through the implementing type, as `Rational::le(a, b)`; through a type parameter under a bound, as `T::le(a, b)`, or through `Self`; by a qualified path, `<T as OrderSpec>::le(a, b)`; through the trait, `OrderSpec::le(a, b)`, where the arguments give the type; and, where it takes `self`, as a method on a logical value. rustc resolves the name by its own rules, among the logic functions in scope, so a name that two traits of one type both declare is ambiguous, as it is in Rust. A logic function and a method of the same name do not conflict: what rustc is given for a logic function has a reserved name ([`compat.names.reserved`](compatibility.md#locus-names)), so a path or a method call of runtime code resolves as it does in Rust with the logic function absent. A method that runs, a law trait's among them, is in scope where the program imports its trait, as in Rust.

r[traits.dyn]
A Locus trait is not used as a trait object: `dyn Tr`, for a Locus trait `Tr`, is rejected wherever it is written. A trait object has no evidence that code could be given, since the implementation behind it is not known where it is used.

## Conversions and operators

r[traits.conversions]
Locus's library has two traits for conversions between logical types. `FromLogic<T>` has the logic function `from(t: T) -> Self`, and `IntoLogic<U>` has the logic function `into(self) -> U`. The library implements `FromLogic<T>` for every logical type `T` itself, as the identity, and `IntoLogic<U>` for every `T` where `U` implements `FromLogic<T>`, so a program implements `FromLogic` and is given `IntoLogic`. A type *converts to `Prop`* when it implements `IntoLogic<Prop>`. `Prop` does, by the identity, and `Bool` does, by the library's one implementation of `FromLogic<Bool>` for `Prop`, under which `b` is the proposition `b === true`. A program writes no implementation of `FromLogic<T>` for `Prop` and none of `IntoLogic<Prop>`, so for now nothing else converts. A logic function may ask the conversion of a parameter of its own, by a type parameter bounded by `IntoLogic<Prop>`, as the library's `iff` does ([`logic.bool.iff`](logical-layer.md#logical-code)). The library has no conversion from `Nat` to `Int`: that is written `n as Int` ([`logic.arith.nat-to-int`](logical-layer.md#logical-types)).

r[traits.operators]
In runtime code an operator, an indexing expression, a `for` loop, `?`, and a method call mean what they mean in Rust. Locus binds none of them to another trait, and no setting changes this. What Locus knows of the result is what the language defines for the built-in types ([Runtime code](runtime.md)), and otherwise the signature of the method that Rust calls, which for a trait of the standard library states no contract ([`contracts.calls.unrelated`](contracts.md#calls)): on a type that has a law trait too, the fact comes from the law trait's own method, called by name. An operator in logical code calls no code that runs. On `Int`, `Nat`, and `Bool` it is built in. On another logical type, each of `+`, `-`, `*`, `/`, `%`, and unary `-` is the logic function of the matching trait of Locus's library, `AddLogic`, `SubLogic`, `MulLogic`, `DivLogic`, `RemLogic`, and `NegLogic`, and each of `<`, `<=`, `>`, and `>=` is a logic function of `OrdLogic` that gives a `Prop`; it is an error where the type does not implement the trait. `==` and `!=` stay defined on `Int`, `Nat`, and `Bool` only ([`logic.eq.comparisons`](logical-layer.md#logical-code)), and the equality of other logical values is `===`.

## Law traits

r[traits.laws.provided]
A law trait of Locus's library provides implementations of traits of the standard library: for each such trait it gives the bodies of that trait's methods, written with the law trait's own members, as `CloneEq` gives `fn clone(&self) -> Self { self.clone_eq().0 }`. Each implementation of a law trait that a program writes or derives generates an implementation of each provided trait for the same type, with the same parameters and bounds, checked like any other code. So the standard method and the law's method run the same code. Where the generated implementation conflicts with another implementation of the provided trait, written, derived, or of another crate, the program is rejected.

r[traits.laws.adapters]
Locus's library may implement a law trait for a type that already implements the provided trait, a type of the language or of the standard library. Such an implementation is an *adapter*: it generates nothing, it names the implementation it stands beside, and its bounds include the law trait for each type parameter on which that implementation calls the provided trait. That the two agree is trusted for each adapter ([`trusted.library-laws`](../design/TRUST.md)), and a result lists each adapter that a contract it uses rests on. Only Locus's library writes an adapter: an implementation of a law trait in a program always generates ([`traits.laws.provided`](#law-traits)).

r[traits.laws.derive]
`#[derive(CloneEq)]` writes an implementation of `CloneEq` by structure. It calls `clone_eq` on each field whose type is not logical, copies each field of a logical type that is not a proof type, and gives each proof field as the original's proof rewritten by the equations that those calls returned. The library can implement `CloneEq` for `Opaque<T>` under `T: Clone`, using ordinary payload cloning and the equality of its `Unit` snapshots; the derive then calls that field implementation normally. Its equality says nothing about the payload's behavior. A field that the type's snapshot cuts ([`models.snapshots.cut`](models.md#snapshots)) is copied where its type is `Copy`, and the derive is otherwise rejected, naming the field. The implementation has the bound `CloneEq` on each type parameter that is not bounded by `Logical`. It is checked like any other code, and it generates the type's `Clone` ([`traits.laws.provided`](#law-traits)), so it is not written beside `#[derive(Clone)]`.

## What has no rule

Three things that [RFC 0006](../design/rfcs/0006-traits.md) says need a second crate or a second file to show, and a litmus example is one file ([multi-file-litmus](../issues/multi-file-litmus.md)). They are stated here without a rule, and become rules when an example can pin them.

- **A Locus trait is implemented only in crates that Locus verifies.** In a build, an implementation of one in a crate that Locus does not verify is an error, wherever it would be used, and there is evidence only for an implementation that Locus checked.
- **The orphan rule is Rust's for logical types too:** a crate implements its own trait for a logical type of Locus's library, and the library's trait for its own logical type, and not the library's trait for the library's type.
- **A trait that another crate declares is read as its crate declared it:** which of its members are logic functions, and which methods run, come from the crate's interface.
