# The logical layer

Locus adds logical types, whose values exist only for checking, and logical code, which computes with them. This chapter says what is logical, where logical values may appear, and what logical code may do. [RFC 0002](../design/rfcs/0002-logical-layer.md) explains the design.

Ordinary types are runtime types or logical types. Runtime types are Rust's types, including the program's own structs and enums. Logical types are `Int`, `Prop`, proof types `@P`, logical function types, tuples of logical types, types declared with `#[derive(Logical)]`, the snapshot type `Snap<T>` of each runtime type `T` that has one, and the logical types of Locus's library, such as `Nat`, which is an `Int` with a proof that it is not negative. The compiler-known empty type `!` has the explicit runtime and logical uses described by `logic.types.never` below.

## What a verified program means

The rules of this specification follow from one reading of a verified program, which [RFC 0002](../design/rfcs/0002-logical-layer.md#what-a-verified-program-means) explains. A verified function means a pure function of values in the logic. A place has a value at each point of the program, and a write gives it a new one, its next *version*; a `&mut` parameter is a value at entry and a value given back, which a signature's result names with `final!`. A proposition is about values, never about places, so it never changes its meaning; a value whose type reads another value is rebuilt when that one changes, with its proofs proved again, which is why a field that an invariant reads ordinarily changes only when the whole value is replaced. The narrow named-acquisition rule suspends observation of the owner and its affected proof fields, and requires an independent proof of their final propositions before restoring access (`contracts.invariants.acquisition`). Every type has an *erased* type, which is what rustc sees, and a meaning in the logic. Code that Locus does not verify is never believed about logical data: it never writes or returns a value whose type exposes logical data, and it is given one only as a loan by shared reference, which it reads and cannot change ([`logic.boundary.loans`](#the-boundary-with-unverified-code)). It may hold a value of a sealed type, whose fields it cannot reach, and what it gives back is known only by its type. Shared mutable state has no value in this reading: Locus knows only the type of what it holds, so that type never changes while the state exists. What this reading cannot express is rejected or opaque, never approximated, and a rule that contradicts it is a defect in the rule.

## Logical types

r[logic.types.never]
The empty type `!` has no constructors and is admitted as a logic function's result type. In logical code an expression of type `!` coerces to an expected logical result type by empty-type elimination. This permits the function `unreachable(p: @False) -> !` of [`proofs.elimination`](proofs.md#proofs); it does not permit a logical loop, panic, or call to runtime code as a substitute for the proof. Runtime `!` keeps Rust's meaning of no normal return, and is not replaced by an inhabited ghost marker. The logical coercion cannot produce executable data or satisfy executable control flow: erasing a call to the logical function cannot make a runtime branch diverge, initialize a runtime value, or make following runtime code unreachable. Rust's runtime `unreachable!()` macro retains its panic behavior and occupies a different namespace from the logical function. Generic `Logical` bounds, logical aggregate positions, and the exact checking/export encoding of `!` are separate gates in [logical-never-lowering](../issues/logical-never-lowering.md); no blanket trait classification follows from these direct uses. Ordinary Rust uses of `!`, including its valid type-argument positions, remain governed by rustc.

r[logic.types.contents-logical]
The fields, payloads, and type arguments of a logical type are logical types, and so are the parameters and ordinary results of a logical function type. The direct empty result `!` follows [`logic.types.never`](#logical-types), without deciding its use as a field or generic argument. The other exception is `Snap<T>`, whose argument names a runtime type.

r[logic.types.tuples]
A tuple type is logical when it has at least one component and all its components are logical. The unit type `()` is a runtime type.

r[logic.types.positive]
A logical type, or a proposition declared with `prop`, refers to itself, directly or through other logical types, generated snapshot types included, only in strictly positive positions: never in a parameter of a logical function type, which includes the premise of `==>`, the operand of `!`, and the domain of `forall` and `exists`.

r[logic.arith.nat-subtraction]
Arithmetic on `Int` and `Nat` is exact. Subtracting one `Nat` from another gives an `Int`, which may be negative.

r[logic.arith.division]
On `Int`, `a / b` is the quotient of `a` by `b` truncated toward zero, and `a % b` is `a - b * (a / b)`, which is zero or has the sign of `a`, as Rust's `/` and `%` on integers are: `-7 / 2` is `-3`, and `-7 % 2` is `-1`. Dividing by zero gives zero, and the remainder of a division by zero is the dividend, as in Lean: `a / 0` is `0`, and `a % 0` is `a`. So `a === b * (a / b) + a % b` for every `a` and `b`. On two `Nat`s, `/` and `%` give a `Nat`.

r[logic.arith.nat-to-int]
A `Nat` is used as an `Int` only where the program writes it as one, `n as Int`. An arithmetic operator, a comparison, `===`, and `!==` take two `Int`s or two `Nat`s, never one of each. And a `Nat` is not accepted where an `Int` is expected: as an argument for a parameter of type `Int`, or as the value of a field, a local, or a result of that type.

r[logic.arith.int-to-nat]
`i.as_nat(p)`, of Locus's library, is a logic function on `Int`: the `Nat` that equals `i`, for a proof `p` of `i >= 0`, so that `i.as_nat(p) as Int === i`. An `Int` becomes a `Nat` in no other way: `as` does not turn an `Int` into a `Nat`, though `4 as Nat` names the type of a literal ([`logic.arith.literals`](#logical-types)).

r[logic.arith.literals]
An integer literal in logical code is an `Int`, or a `Nat` where a `Nat` is expected, as it is beside a `Nat` in an operator, as an argument for a parameter of type `Nat`, and as the index of a sequence ([`core.sequences`](core.md)). A literal of which nothing is expected is an `Int`, whatever a later use of it wants ([`logic.ghost.types-forward`](#ghost-values)). Where a literal is the argument for a parameter whose type is a type parameter of the function called, nothing gives it a type, and the program writes one: `4 as Nat` or `4 as Int`.

## Ghost values

Values of logical types, proofs included, are *ghost*: they exist only for checking. They may appear in logical code, as parameters, results, locals, and fields of logical type, and inside runtime types as type arguments.

r[logic.ghost.erased]
Values of logical types have no runtime representation. At run time, a ghost value is a zero-sized marker: `Proof` for a proof, whatever it proves, and for any other logical value a marker of its logical type's own, so that a `Nat` and an `Int` are two types to rustc. A marker carries no proposition and no value. Inside a runtime type and as the type of a field, a logical type is its marker, and a tuple keeps its shape, with a marker for each logical component. Logical code is never evaluated at run time. The special never-type uses follow [`logic.types.never`](#logical-types): this marker rule never turns executable `!` into an inhabited type or uses an erased logical call to establish executable divergence.

r[logic.ghost.marker-traits]
`Proof`, the marker of every proof, implements `Clone`, `Copy`, `Debug`, `PartialEq`, `Eq`, `PartialOrd`, `Ord`, and `Hash`, which are right for proofs because any two proofs of a proposition are equal. Under `Debug` it prints as `Proof`. The marker of every other logical type implements only `Clone`, `Copy`, and `Debug`, of the traits of the standard library. Every marker, `Proof` among them, also implements `Logical` and `CloneEq` of Locus's library, whose method copies it ([`traits.laws.provided`](traits.md#law-traits)). These are all the traits with a method that runs that a logical type implements: a program adds none ([`traits.impls.logical-types`](traits.md#implementations)). None implements a trait that makes a value from nothing, such as `Default`.

r[logic.ghost.types-forward]
Locus never infers a logical type backward from a later use. A local whose type holds logical values gets that type from its annotation, or from what initializes it: a call's result, Locus syntax, or another value whose type is known.

r[logic.ghost.type-identity]
Two types that hold logical values are the same type only when they are built the same way from the same types, and from propositions that convert to the same core term ([`core.conversion`](core.md)): the same formula, up to evaluation, about the same values. rustc compares only markers, so Locus checks this wherever one type must match another: an argument against its parameter, an assigned value against its place, an initializer against its field, every use of a type parameter against the others, and the associated type that a bound binds, as `P` in `T: Claim<P = @False>`, against the associated type of the implementation that rustc resolved for it ([`traits.impls.headers`](traits.md#implementations)). A proposition that reads another version of a place makes a different type, and so does one that is equivalent only by a proof, such as `0 < n` for `n > 0`. A proof by value is proved again instead, and a value that holds one is rebuilt from its parts.

r[logic.ghost.dependent-tuples]
A tuple type in which a later component's proposition reads an earlier component is one type. It instantiates a type parameter only as a whole, and never matches a generic tuple type such as `(A, B)`, whose components could then be replaced separately. A pattern takes such a tuple apart.

r[logic.ghost.interior-mutability]
A type with interior mutability may hold logical values. Its contents are part of no version, no snapshot, and no model, so Locus knows only their types: a proof taken out of a `Cell<Option<@P>>` is a proof of `P`, and a `Nat` taken out of a `Cell<Nat>` is some `Nat`. So the type of what such a type holds never changes while it exists: a proposition under interior mutability, at any depth, reads only what is fixed where its type is written, which is a local or a parameter at that point, a constant, or an immutable static. In the type of a field it reads no other field of the value, and in the type of a tuple component it reads no other component.

r[logic.ghost.runtime-parts-kept]
A runtime type that holds logical values keeps its runtime parts: an `Option` keeps its tag, and a `Vec` its length. Building one with a proof in it needs that proof, and taking the proof out gives back a proof of the same proposition.

r[logic.ghost.runtime-code-kept]
Erasure removes only logical code. A runtime call, condition, or statement runs as written, even when the expression it belongs to has a ghost value.

r[logic.ghost.generic-instantiations]
The boundary is checked for each instantiation. The program's own verified generic code is checked again at each instantiation whose type arguments expose logical data, and such an instantiation is rejected when a value whose type mentions one of those parameters reaches unverified code, in the function's body or in what it calls, other than as a loan ([`logic.boundary.loans`](#the-boundary-with-unverified-code)). A verified generic function's interface records, for each type parameter, how a value whose type mentions it reaches unverified code, in the function's body or in what it calls: never; only as loans, and then the type of each value that is lent, written in the function's own type parameters; or in some other way. So an instantiation made in another crate, which is checked without the body, is accepted for a parameter recorded as never; is accepted for one recorded as only lent when each recorded loan meets [`logic.boundary.loans`](#the-boundary-with-unverified-code) at the caller's type arguments; and is otherwise rejected. An unverified generic function is never instantiated with a type that exposes logical data ([`logic.boundary.plain-data`](#the-boundary-with-unverified-code)), except to be lent a value of it.

r[logic.ghost.no-runtime-control]
Runtime control flow never depends on a logical value.

r[logic.ghost.positions-logical]
An argument for a proof parameter, or for a parameter of logical type, is a binding that holds a ghost value, or logical code, never a call of a runtime function. Elsewhere, a runtime call that produces a ghost value stays where it is. Outside logical code, a runtime value is never captured implicitly: where a ghost value is expected, as such an argument or as the initializer of a logical field or a ghost local, a runtime value is written as logical code, such as `logic! { x }`.

r[logic.ghost.shown-by-source]
Outside delimited logical code, a binding is *shown to be ghost* only when it is a parameter of logical type, its type annotation holds a logical type, it is initialized by logical code, or it is bound by a proof pattern. An operator, method call, or field access there is logical code only when each operand is logical code or a binding shown to be ghost. Any other ghost value can be passed on and stored, but computing with it needs `logic!`.

r[logic.ghost.no-trait-impls]
A logical type appears in an `impl`'s self type, in its trait's arguments, and in its associated types, and a trait method's signature holds logical values, only as [Traits](traits.md) allows: a trait declares the logical values that its methods' signatures hold ([`traits.members`](traits.md#what-a-trait-holds)), no proof type and no snapshot type is written in a header ([`traits.impls.headers`](traits.md#implementations)), and a program gives a logical type no trait with a method that runs ([`traits.impls.logical-types`](traits.md#implementations)). A runtime type that holds logical data may implement a trait; its methods take `Self`, so they are verified ([`logic.unverified.functions`](#unverified-functions-and-unsafe-code)), and unverified code may call them on a value of a sealed type.

r[logic.ghost.no-unions]
No field of a union has a type that holds a logical type ([`logic.unverified.plain-rust`](#unverified-functions-and-unsafe-code)), at any depth, as `Option<@P>`, `ManuallyDrop<Interval>`, `ManuallyDrop<Vec<Interval>>`, and `Nat` do. Reading another field would make its value from memory of a different type; and reading a union needs `unsafe`, so only an unverified function could read it, and none takes such a type.

## The boundary with unverified code

r[logic.boundary.unverified]
*Unverified code* is code that Locus does not verify: the crate's own unverified functions ([`logic.unverified.functions`](#unverified-functions-and-unsafe-code)), its plain-Rust dependencies, the standard library, and code reached from any of these through trait objects or function pointers. The operations that the language itself defines on Rust's built-in types, such as arithmetic, the length and indexing of arrays and slices, and building and matching an `Option`, are not calls of unverified code. When a crate is exported, every crate that uses it is unverified too. All other code of a Locus crate is *verified code*.

r[logic.boundary.logical-data]
A type *holds logical data* when a logical type appears in it at any depth: as the type itself; as a type argument or a tuple component; in a field of a struct, an enum, or a union that it names, private fields and the types of other crates included; in the parameters or the result of a function, a function pointer, or a closure; in what a closure captures; and in the type that an `impl Trait` or another opaque type hides. A struct or enum of a verified crate that holds logical data only in the declared types of its own fields, with none coming in through a type argument, is a *sealed type*. A type *exposes logical data* when it holds some that is not inside the fields of a sealed type. So `@P`, `Option<@P>`, `Vec<Nat>`, and a function that takes a proof expose logical data; a struct with a proof field holds logical data and exposes none, and neither does a reference to one, a vector of them, or a closure that takes one. A value whose type exposes logical data is never converted to a trait object, whose type would hide what it holds, except as a loan ([`logic.boundary.loans`](#the-boundary-with-unverified-code)).

r[logic.boundary.plain-data]
No exposed logical data reaches unverified code, apart from the two exceptions below. After type parameters are instantiated, no unverified function has a parameter, a result, or a type argument whose type exposes logical data, and none names a function, a static, or a constant whose type does. So verified code never gives unverified code a value whose type exposes logical data, whether by value, by mutable reference, inside another value, or captured in a closure, and never calls it at such a type; and unverified code calls a verified function only when that function's instantiated signature, its receiver included, exposes none. Unverified code may hold a value of a sealed type: it can move the value, drop it, and call the type's own functions on it, and what it gives back is a value of that type. One exception is inside Locus's own library: the types it provides in place of the standard library's collections, reference-counted pointers, cells, and locks keep the values they are given in the standard library's own types, and that is trusted, not checked ([`trusted.library`](../design/TRUST.md)). So a `Vec` or a `Cell` of Locus's library may hold exposed logical data, and the standard library's own `Vec::push`, `Option::take`, and `Cell::set` are unverified code, as `black_box` and `Any::downcast` are. A value of Locus's type reaches the standard library's type by shared reference only ([`collections.std-inside`](collections.md#the-standard-librarys-collection-inside)). A method of the standard library's type that it reaches through `Deref`, which is one that takes `&self`, is the standard library's own function too, and is judged as every call of unverified code is: at a type that exposes logical data it is rejected, apart from a loan. A method of the standard library's type that takes `&mut self` is not reached at all. The other is a loan ([`logic.boundary.loans`](#the-boundary-with-unverified-code)).

r[logic.boundary.loans]
Unverified code may be lent exposed logical data that it cannot change. After type parameters are instantiated, a parameter of an unverified function may be a shared reference to a value whose type exposes logical data, when every logical type in that type lies in the structural part of the value's snapshot ([`models.snapshots.opaque`](models.md#snapshots)): none inside an `UnsafeCell`, behind a raw pointer, or in a type whose snapshot is opaque or that has none ([`models.frozen-data`](models.md#snapshots), [`models.snapshots.seen`](models.md#snapshots)), and none in the signature or the captures of a function, a function pointer, or a closure. A type argument of the function may then expose logical data, when the instantiated signature holds it only inside such parameters. In verified code, a shared reference to such a value may be converted to a shared reference to a trait object whose own type holds no logical data. Nothing else is relaxed: the function's result and its other parameters expose no logical data, whether or not the caller uses the result. So unverified code reads what it is lent, cannot change it, and gives nothing logical back, and a marker that it copies out of a loan reaches no verified code.

r[logic.boundary.calls]
A function or closure whose signature exposes logical data is called only by verified code, each call checked against its contract. It is never coerced to a function pointer and never turned into a trait object; it is not an `extern`, `#[no_mangle]`, or `#[export_name]` function; and it is passed as a value only within verified code, to a generic parameter only of the program's own verified code, never to unverified code and never to a library operation, which could call it with arguments that its contract does not allow.

r[logic.boundary.foreign]
Only plain data crosses to foreign code, which is code that is not compiled from Rust. After type parameters are instantiated, no type that holds logical data ([`logic.boundary.logical-data`](#the-boundary-with-unverified-code)), sealed or not, appears in the signature of a function of a Locus crate that foreign code can call: one defined with an ABI that is not Rust's, or with `#[no_mangle]` or `#[export_name]`, or one that a `sym` operand of `asm!`, `global_asm!`, or `naked_asm!` names, since assembly that is given a function can call it with any arguments. Nor does one appear among the parameters or as the result of a function pointer type whose ABI is not Rust's, wherever that type appears in a Locus crate, written or inferred. As everywhere, a type holds logical data at any depth, so through a reference, a `Box`, and a raw pointer. The signature of a function declared in an `extern` block ([`logic.unverified.plain-rust`](#unverified-functions-and-unsafe-code)) and the type of a static that foreign code can reach ([`logic.code.statics`](#logical-code)) are held to the same. Foreign code could fill a value of such a type with any bytes, and reach the fields of one it is given. A function that foreign code can call is otherwise as any other function: it is verified or unverified by [`logic.unverified.functions`](#unverified-functions-and-unsafe-code), for which the `unsafe` of `#[unsafe(no_mangle)]` and `#[unsafe(export_name)]` is not `unsafe` code, and a verified one may build and use values that hold logical data in its body.

r[logic.boundary.escape]
A call changes only what its arguments let it change, and only while it holds them. A call may write a place only through a value it is given that reaches the place mutably. Which places a value can reach is decided from rustc's borrow facts, not from the value's visible type: a place is reachable when a loan of it flows into a lifetime of the value's type, mutably for a mutable loan and, for a shared loan, only where it reaches interior mutability, so a `&mut` held by a trait object, an opaque type, a closure, or a container counts. For verified code this follows from its verification; for unverified code it is the assumption [`assumed.unsafe.sound`](../design/TRUST.md). It holds for implicit calls too: a drop, an overloaded operator, or a callback. When the borrow ends, the place has a new version. Its value is what the contract of a verified function says, and otherwise unknown: Locus knows it only by its type, which for a sealed type includes its proof fields, and proofs about its earlier versions say nothing about it, until a write it sees makes a fact about it hold again. Once the borrow has ended, no later call changes the place, whatever the code that held the borrow did with its address. A value that unverified code returns is known only by its type, proof fields included, and from then on belongs to the code that received it. A verified function's summary says which of the places it is given it may write; an unverified function may write every place it is given mutably. The summary is computed from the function's body and the functions it calls; how is the runtime semantics ([runtime-semantics](../issues/runtime-semantics.md)).

## Unverified functions and unsafe code

r[logic.unverified.functions]
Every function of a Locus crate is verified or unverified. A function marked `#[verified]` is verified, and one marked `#[unverified]` is unverified. Without a mark, a function whose signature, its receiver included, holds logical data is verified. Any other function is unverified when it is an `unsafe fn`, when it is a naked function, `#[unsafe(naked)]`, whose body is assembly, or when its body, after macro expansion and including the closures written in it, contains an `unsafe` block or an expression whose type is a raw pointer, before or after coercion; otherwise it is verified. A function nested in another is judged by itself, and a foreign function is unverified. The initializer of a `const` or a `static` is treated as a function body. Verified code knows an unverified function only by its Rust type, as it knows a function of an unverified crate ([`logic.boundary.escape`](#the-boundary-with-unverified-code)).

r[logic.verified.restrictions]
A verified function is not an `unsafe fn` and not a naked function, and its body contains no `unsafe` block and no expression whose type is a raw pointer; `unsafe` that the compiler itself generates for an operation it has checked does not count. A mark chooses a function's kind and never waives a rule: a function that is verified by its mark or by its signature, and that breaks this one, is rejected. Where Locus has something to verify and cannot, the function is rejected, and never becomes unverified instead. A verified function with no logical code and no logical data has nothing to prove, and is accepted whatever Rust it uses.

r[logic.unverified.plain-rust]
An unverified function of a Locus crate is plain Rust. It holds no logical code: no proof parameter, proposition, proof, or proof hole, and no `logic!` or `prove!`. No type that holds logical data ([`logic.boundary.logical-data`](#the-boundary-with-unverified-code)) appears in its signature, in the type of an expression or pattern in its body, or in the signature of a function or the type of a static that its body names, so `#[unverified]` on a function whose signature holds logical data is rejected. So such a function handles no proof, no logical data, and no value of a type with proof fields, sealed or not, since it could reach the type's fields. The signature of a foreign function is held to the same rule. A type parameter of an unverified function is never instantiated with a type that exposes logical data ([`logic.boundary.plain-data`](#the-boundary-with-unverified-code)), except to be lent a value of it ([`logic.boundary.loans`](#the-boundary-with-unverified-code)); it may be instantiated with a sealed type, which the function as written does not name.

r[logic.unsafe.invariant]
A sealed type's proof fields are an obligation that Locus places on `unsafe` code beyond Rust's own: every value of the type satisfies them. The crate's own unverified functions meet it by handling no type that holds logical data ([`logic.unverified.plain-rust`](#unverified-functions-and-unsafe-code)), so no function of the crate makes such a value from memory of another type, by `transmute`, by a pointer cast, or by `mem::zeroed`. Generic `unsafe` code meets it when it is sound, since it cannot name the type's fields; other `unsafe` code, in the crate's dependencies or in unverified crates that use the crate, meets it as a trusted assumption, which a hand-written `unsafe impl` records for its type.

## Logical code

Logical code is the bodies of logic functions and proposition declarations; the contents of `logic!`, `prop!`, and `prove!`; propositions in types and proof holes; calls of logic functions and proof constructors; and operators on bindings shown to be ghost. In it, a runtime place that is read is captured: it stands for its language-generated [snapshot](models.md).

r[logic.code.logical-values]
Logical code computes only with logical values and is total on its valid arguments. A logic function's result type is logical, or the empty result `!` admitted by `logic.types.never`; the latter gives no value on an impossible input. A runtime value enters logical code only where logical code reads a place, and is a logical value there: its language-generated snapshot, whether capture is implicit or written `snap` ([`models.observation`](models.md#models)).

r[logic.fn.parameters]
Each parameter of a logic function has a logical type, which `Snap<T>` and the result type of an explicit view are. A parameter written with a runtime type, such as `xs: &[u32]`, or `self` in an `impl` of a runtime type, is rejected. A runtime place given as an argument is its capture ([`models.observation`](models.md#models)), whatever the type of the parameter, and `snap(x)` gives its snapshot. A type parameter of a logic function ranges over logical types, unless it is bounded by `Snapshot`: it then stands for any type that has a snapshot, a runtime type or a logical one ([`models.snapshots.seen`](models.md#snapshots)), of which the function names `Snap<T>`, and takes no value of type `T` itself.

r[logic.eq.same]
`a === b` is the proposition that the logical values `a` and `b` are equal, and `a !== b` its negation. Every logical type has it, and it cannot be overloaded. On pure logical function values it is extensional: pointwise `===` at every argument yields function `===` through the explicit theorem [`proofs.equality.funext`](proofs.md#constructing-proofs).

r[logic.eq.runtime-values]
On runtime places, `a === b` compares their snapshots. No view is applied; adding a view changes no equality. Explicitly comparing view results gives only that chosen abstraction's equality, not equality of its input snapshots.

r[logic.eq.snapshots]
Snapshot equality compares retained variant tags and component observations. `Unit` components from `Opaque` and `UnsafeCell` contribute no distinction. Supported abstract external snapshots are not singletons. Equality of snapshots implies neither equal omitted state, equivalent arbitrary runtime calls, aliasing, nor interchangeable permissions.

r[logic.eq.comparisons]
`==`, `!=`, `<`, `<=`, `>`, and `>=` in logical code give a proposition, of type `Prop`, and never a `Bool`. For now they are defined only on `Int`, `Nat`, and `Bool`, on two operands of one type, where `a == b` holds exactly when `a === b`, `a != b` exactly when `a !== b`, and each ordering agrees with the order of the integers. In a core term a comparison is the proposition that a `Bool` is `true` ([`logic.bool.as-proposition`](#logical-code)), so what this specification says of a `Bool` used as a proposition, it says of a comparison.

r[logic.bool.as-proposition]
A `Bool` is the snapshot of a runtime `bool`, and the type of `true` and `false`. A value of a type that converts to `Prop` ([`traits.conversions`](traits.md#conversions-and-operators)), which a `Bool` is, and for now nothing else but a proposition itself, is used as a proposition, with nothing written, at the positions where the form of the code requires a proposition: as the proposition of a proof type `@( .. )`, and of `prop!( .. )` and `prove!( .. )`; as the body of a `forall` or an `exists`; as an operand of `==>`; as an operand of `&&` or `||` whose other operand is a proposition; as the body of a logic function declared to return `Prop`; and as an argument for a parameter whose type is a type parameter bounded by `IntoLogic<Prop>`, as each parameter of `iff` is ([`logic.bool.iff`](#logical-code)). There a `Bool` `b` stands for the proposition `b === true`, which is what the library's conversion gives. `&&`, `||`, and `!` whose operands are all `Bool`s are operators on `Bool`s and give a `Bool`, wherever they are written. At every other position a `Bool` is not a `Prop`: as an argument for a parameter of type `Prop`, or as the value of a local or a field of that type, it is written `b === true`.

r[logic.bool.iff]
`iff(p, q)`, of Locus's library, is a logic function that gives the proposition `(p ==> q) && (q ==> p)`. Each of its two parameters takes a proposition or a `Bool`, and takes nothing else: a `Bool` there stands for the proposition that it is true ([`logic.bool.as-proposition`](#logical-code)). Logical code has no connective for "exactly when", and no function from a proposition to a `Bool`. A contract ties a `bool` result `r` to a proposition `P` as `iff(r, P)`, or with two implications, and the `Bool` of a proposition `P` is written `if P { true } else { false }`.

r[logic.code.no-runtime-calls]
Logical code does not call runtime functions or methods, and does not mutate runtime state.

r[logic.fn.total]
Every recursive call of a logic function is on a structurally smaller part of one of its arguments, or decreases the function's declared measure. A measure is a `Nat` or an `Int`. At each recursive call, the measure at the call's arguments is smaller than at the parameters and is not negative, which for an `Int` is part of what is proved. For now, no logic function calls itself through another. A body that proof search completes is held to the same rule.

r[logic.const.well-founded]
A constant of logical type is not defined in terms of itself, directly or through other constants or logic functions. The same holds for the logical data in the initializer of any constant or static whose type holds some: it does not depend on the item itself, directly, through other constants and statics, through logic functions, or through a field of the item. While an initializer is checked, the proof fields of the item it initializes are not available. A cycle of addresses among statics is not such a dependence. In the initializer of a `const` or a `static`, an associated constant's included, every proof comes from logical code alone, a proof field's included: none is the result of a runtime call, a `const fn` included, or part of a value that a runtime call returns. rustc evaluates an associated constant of a generic `impl` only for a use in code that it compiles, which a use in logical code is not, so nothing would make such a call return.

r[logic.code.statics]
Logical code reads a static only when it is immutable. No `static mut`, no static that is `extern`, `#[no_mangle]`, or `#[export_name]`, and no static that a `sym` operand of `asm!`, `global_asm!`, or `naked_asm!` names, has a type that holds logical data.
