# Runtime code

What Locus knows about the values that runtime code computes. A proof is about values, and this chapter says which facts about them the language gives at each point of a function. [RFC 0004](../design/rfcs/0004-runtime-code.md) explains the design.

## The context

r[runtime.facts]
What Locus knows at a point of a function is the proofs in scope there and the *context*: facts about value names ([`core.values`](core.md)). Each fact has one source, a rule of this chapter: an understood operation or a call that has returned, a condition that was evaluated, a write, the bounds of a `for`, a join, the end of a borrow, or the top of a loop. A fact is in the context only at points that execution reaches after its source, and no rule gives a fact because a proof asks for one.

## Understood operations

r[runtime.operations]
Locus understands an operation of runtime code when it is in one of two closed lists, matched by what rustc resolves the operation to and by the full types of its operands. The first list is what the language defines: arithmetic, division, and remainder on machine integers; comparisons between two machine integers of one type, or between two `bool`s; `&&`, `||`, `!`, `&`, `|`, and `^` on `bool`s; a cast from an integer or a `bool` to an integer type; literals and constants; field and tuple access; building a tuple, a struct, or an enum; taking a reference, and following a reference or a `Box`; indexing an array or a slice by a `usize`; assignment, and compound assignment as the operation followed by the write; and `if`, `match`, `if let`, and `let` with a pattern (`runtime.patterns`). The second list is library items whose meaning Locus fixes: `len` on arrays and slices; `Box::new`; `checked_add`, `checked_sub`, and `checked_mul` on the integer types; range indexing of arrays and slices; `for` over a range of integers; and `?` (`runtime.try`). `put` on a slot of Locus's library is a write to the place that the slot was taken from ([`contracts.slots`](contracts.md)). Every other operation, and every other call of a function or a method, gives only what a callee's signature says ([`contracts.calls.unrelated`](contracts.md)): among them a comparison on any other type, a shift, and `&`, `|`, `^`, and `!` on integers.

r[runtime.operations.returned]
Each understood operation has a value, which is a logical expression of its operands, and a condition under which it returns. Once the operation has returned, Locus knows that the condition held and that the result is the value. It knows neither before the operation.

r[runtime.operations.conditions]
Indexing an array or a slice returns only if the index is less than the length. Range indexing returns only if: for `a..b`, `a <= b` and `b` is at most the length; for `a..=b`, `a <= b + 1` and `b` is less than the length; for `a..`, `a` is at most the length; for `..b`, `b` is at most the length; and for `..=b`, `b` is less than the length. Division and remainder return only if the divisor is not zero and, for a signed type, the quotient is in the type's range. Every other understood operation always returns. `checked_add`, `checked_sub`, and `checked_mul` give `Some` of the true result when it is in the type's range, and `None` otherwise. A cast between integer types gives the value wrapped to the target type, and a cast from a `bool` gives 0 or 1.

r[runtime.arith.wrapping]
`+`, `-`, and `*` on machine integers, and negation, give `wrap` of the true result at the operation's type ([`core.wrap`](core.md)), whichever way the crate is built, and Locus takes no fact from one of them having returned. A cast between integer types gives `wrap` of its operand at the target type. When the true result is in the type's range, `wrap` of it is the true result.

r[runtime.conditions]
The condition of an `if`, a `while`, or a `match` guard is evaluated once, to a `Bool` term over the value names of its operands, in Rust's order of evaluation: an understood operation contributes its value, and a call the value name of its result. Where the condition held, that term is in the context, and where it did not, its negation is. A `while` that ends because its condition did not hold gives the negation after the loop.

r[runtime.patterns]
In an arm of a `match`, in the body of an `if let`, and after a `let` with a pattern, the context holds that the scrutinee matched the pattern, for a pattern built from bindings, wildcards, literals, ranges of integers, references, and the constructors of tuples, structs, and enums. In an arm of a `match` it also holds, for each earlier arm, that its pattern did not match or its guard did not hold. A slice pattern gives no fact about the sequence it matches.

r[runtime.try]
`e?` is understood in two cases, decided by what rustc resolves it to: `e` is an `Option` and the function or closure that it returns from returns an `Option`; or `e` is a `Result` and that function or closure returns a `Result`. It continues with the payload of a `Some` or an `Ok`, and the context then holds that `e` was one with that payload. Otherwise it returns: for an `Option`, `None`; for a `Result` whose error type is the returned one's, an `Err` with the same error; and for one whose error type differs, an `Err` whose error is the result of a conversion, which is a call. In every other case, such as a function that returns a `Poll`, `e?` runs as Rust defines it and gives no fact: the value it continues with is known by its type. `?` is not accepted on a value whose type holds logical data, for now.

r[runtime.debug-assertions]
`cfg!(debug_assertions)` is a `bool` of which Locus knows nothing, in every build, and a branch on it is checked as a branch on any unknown condition: what it writes is joined with what was there before, and a fact established inside it is not known afterwards (`runtime.joins`). So the condition of a `debug_assert!`, a `debug_assert_eq!`, or a `debug_assert_ne!` is not known after it. A statement or a block under `#[cfg(debug_assertions)]`, or under its negation, is checked, where the configuration has it, as the body of such a branch. This limits what a proof may rest on. It does not make a proof hold in a configuration that was not checked: an item under that `cfg`, like every other `cfg`, is as the configuration being built has it.

## Writes and borrows

r[runtime.writes]
A write gives the place it writes a new value name ([`proofs.versions`](proofs.md)). After a write to a field, the value that holds the field has a new name too, equal to its old value with that field replaced. After a write to an element of an array or a slice, the sequence has a new name, equal to the old one updated at that index and of the same length; the write returns only if the index is less than the length.

r[runtime.borrows]
A field of a struct, a component of a tuple, and a field of an enum's variant are places of their own, each with its value names, and the value of the whole at a point is its constructor applied to the values its parts have there. A mutable borrow of a place suspends that place's value name while the borrow lives, and no other place's: a sibling keeps its name, and may be read, written, and borrowed. The target of the reference has value names of its own: the first equals the value the place had, and each write through the reference gives it a new one. When the borrow ends, the value it ends with ([`contracts.final`](contracts.md)) equals the target's value name at that point, and the place gets a new value name equal to it. A borrow of one element by indexing, as in `&mut xs[i]`, suspends the whole sequence, which rustc lets nothing else borrow meanwhile, and at its end the sequence is its earlier value updated at that index. Where a pattern lends several elements, or a part of a slice, at once, Locus keeps no fact about the elements when those loans end: the sequence gets a new value name, known to have the length it had. A reborrow is a borrow of a place inside the target, and ends the same way. Where reborrows outlive the function that made them, as when they are returned, the value the outer borrow ends with is known there as the constructor applied, for each part, to the value its reborrow ends with when one is outstanding, and to the part's current value when none is. A borrow given to a call ends when the call returns, unless something else in the callee's signature can hold it, as rustc decides from the signature ([`contracts.final`](contracts.md)): its result, or a place that another parameter lets the callee write. Then it ends when whatever holds it is used for the last time. Either way the caller then knows of the place what the callee's proofs say of the value the borrow ended with. A part that has been moved out has no value name until it is initialized again, and while a part has none the whole has no value: its other parts are still places of their own.

## Proofs that are kept

r[runtime.proofs.assigned]
A proof variable declared with `let mut`, of a type `@P`, has its proposition written at its declaration, as a template over the places it reads. Each assignment makes a new version of the variable's contents, whose type is the template at the value names those places have at that point, and the assigned proof is checked against it. No version is ever given another type: after one of those places is written, the variable still holds a proof about the earlier values, which does not fit where a proof about the current values is required ([`proofs.versions`](proofs.md)). Locus does not assign it again by itself. Such a variable is not mutably borrowed, and no closure assigns it. A `let mut` local of any other type that holds a proof keeps the propositions of its declaration ([`logic.ghost.type-identity`](logical-layer.md)).

r[runtime.joins]
Where the branches of an `if` or a `match` meet, a place that some branch wrote gets a new value name, with the fact that it equals the `if` or the `match`, on the evaluated condition or scrutinee, of the values it had at the end of each branch. A fact that held at the end of only some branches is not in the context afterwards. A proof variable gets a new version there, which Locus builds by cases from the versions at the end of each branch: it proves the variable's proposition at the new value names when every branch's version did at that branch's, and otherwise it proves the `if` of the branches' propositions. A branch that does not reach the meeting point, because it returns, breaks, or panics, takes no part.

r[runtime.loops]
At the top of a loop, each place that the loop writes gets a new value name, about which the context holds no fact. A proof variable that the loop assigns is an invariant of the loop when its version proves its proposition at the value names of the path into the loop, and at those of every path from the body back to the top, a `continue` included. Locus checks each of those, and then checks the body with a version that proves the proposition at the top's new value names. A proof variable that the loop assigns and that is not an invariant has no version at the top, and reading it before it is assigned again is an error. One that the loop does not assign keeps its version. Leaving the loop because its condition did not hold carries what is known at the top, with the negated condition; leaving by `break` carries what is known at the `break`; and where those meet, a place that they leave with different names gets a new one. Locus asks for no proof that a loop ends.

r[runtime.loops.for-range]
`for i in a..b` evaluates `a` and then `b` once, before the first iteration. In its body, with `lo` and `hi` the values they had then, `lo <= i && i < hi` is in the context, and for `a..=b`, `lo <= i && i <= hi`. This is a fact about those two values, and about a place that `a` or `b` reads only while that place has not been written since. In any other `for` loop, the loop variable is known by its type.
