# Contracts

A runtime function states its contract in its signature: proof parameters are preconditions, and proofs in its result are postconditions. There is no other form: no separate clause states a precondition, so a signature without logical data asks nothing of its caller. Types state invariants in proof fields. [RFC 0002](../design/rfcs/0002-logical-layer.md) explains the design.

## Values in a signature

r[contracts.entry-values]
In a function's signature, each parameter denotes its value when the function is called. For a `&mut` parameter, that is the value of its referent at entry. A closure's signature is not a contract yet ([closures-async-packed-macros](../issues/closures-async-packed-macros.md)), and until it is, a proposition in the type of a closure's parameter, a proof parameter's among them, mentions no place that the closure itself writes, directly or by a call: no variable that it captures by value and assigns, none that it captures by mutable reference and writes or lends mutably, and no place that it writes through a reference it captures.

r[contracts.final]
`final!(r)` denotes the value that the referent of the mutable reference `r` has when the borrow ends: when neither `r` nor any reborrow of it is used again. When the borrow ends, the place that was borrowed holds that value. Where the place that holds `r`, or a reference that carries its borrow, is written in one of the ways that [`runtime.borrows`](runtime.md) says leave nothing known of the value the borrow ends with, as `*pp = &mut b` and `mem::swap(&mut r, &mut s)` do, the place still holds `final!(r)`, and nothing is known of it: writes through what the place holds afterwards say nothing of it. `final!` appears in the propositions of a signature's result, where `r` is a `&mut` parameter or a `&mut` in the result. In a body it may also name a local mutable-reference binding, including a parameter binding, while the loan it denotes is live, and only in proofs and their propositions as `contracts.final.pending` requires. It never appears in a parameter's type. There is no form that chooses a loan by naming an arbitrary borrowed place: `final!(r)` always denotes the final referent value of the reference binding `r`, with the reference-replacement restrictions above. A source use after that loan has ended is rejected; capture the current place to name its value then. What a body may do with a final value that a proof it holds mentions is `contracts.final.pending`. For a `&mut` parameter whose lifetime nothing else in the signature can hold, as rustc decides from the signature, counting the lifetimes that an `impl Trait` result or an `async fn` captures without naming them, the borrow ends when the function returns, after its locals are dropped. `final!(r)` reads no place.

r[contracts.final.pending]
Until a mutable borrow ends, every occurrence in a core term of the value it ends with lies inside a term of a proof type, or inside the proposition of a proof type. So the value may appear in a proof, in any part of one, such as an argument of a lemma, and in what a proof proves. A term of any other type that mentions it, and that is not part of a proof, is rejected: it would be a value of its own, to bind, store, return, or pass to a function whose result is not a proof. `Prop` is no exception, since a proposition is a logical value that can be stored and read back. The check is on core terms, so it does not matter how the value got into one: inferred for a `_`, or returned by a logic function. A proof about a borrow's final value may be bound, combined with other proofs, and returned before the borrow ends. Once the borrow has ended, the value is the one the place holds ([`runtime.borrows`](runtime.md)), and nothing restricts it.

## Calls

r[contracts.calls.unrelated]
What verified code knows about the result of a call is what the callee's contract says, a proof in its result, and nothing else: no fact is attached to a function from outside its signature. Two calls of one function with equal arguments are unrelated unless such a proof relates them: a fact about the result of the first is not a fact about the result of the second.

## Proofs in data

r[contracts.invariants]
Every value of a type with proof fields satisfies them. Each construction of the type proves them, including constructions in code that macros and derives generate, and a struct update.

r[contracts.invariants.reads]
A proof field *reads* the fields that its proposition mentions. A proposition in the type of a field mentions only other fields of the same struct, variant, or tuple, and constants: never a field whose type is a proof type, and never the value as a whole. It reads a field through its owned parts, a `Box`, and a shared reference, and never through a `&mut` or into a type with interior mutability. Nor does it read into an abstract external snapshot ([`models.snapshots.opaque`](models.md)), which a call that is given the value by shared reference may change. It reads nothing behind a reference in a field that the type's snapshot cuts ([`models.snapshots.cut`](models.md)): the snapshot holds only an address there, so the proof field's proposition would speak of what its own value does not hold. When it mentions a field whose own type has proof fields, it reads that whole field.

r[contracts.invariants.no-mutable-borrow]
No place based on a proof field is mutably borrowed. A place based on a field that a proof field reads is mutably borrowed only by the named acquisition of `contracts.invariants.acquisition`; every other form is rejected, including a direct returned borrow, `ref mut`, a closure's capture, or a binding that a pattern makes by reference when it matches through a `&mut`.

r[contracts.invariants.acquisition]
A verified function may acquire a mutable loan of a field that a proof field reads with an immutable local binding `let r = &mut place;`. The binding has exactly one runtime use, as the receiver or the argument itself of one synchronous call, with Rust's ordinary implicit reborrow, and is not used again, reassigned, captured, stored or returned. A proof-only mention of `final!(r)` is not a runtime use. The field is identified when the borrow is taken; the binding names that acquisition loan, not whichever reference later occupies another place. Explicit `&mut` activates immediately, so arguments that read the owner are computed before taking the loan. From acquisition until both the loan has ended and its preservation obligation has been checked, no proof field that reads the lent place or a place it is based on, at any enclosing level, is read or lent; evidence about their entry values is copied before acquisition. The affected owner is unavailable as a whole while suspended. Other dependencies of those proof fields retain their existing assignment and borrowing restrictions. At most one such acquisition is live for each affected proof field.

On normal return from the call, before any further runtime operation (including a drop or control-flow exit), a proof-only region must establish each affected proof field's proposition with the lent place replaced by its final value, using frozen entry evidence and the call's result proofs. This is a kernel-checked obligation, not an assumption of the suspended invariant and not an assignment to the suspended proof field. Its certificate cannot depend on an affected proof field at the changed or pending-final owner version, even through a snapshot projection, a lemma, a type-derived fact, or evidence bound before acquisition. Only facts about the actual entry value may be copied as entry evidence; the affected owner's eventual validity is not a premise. This is a dependency check on elaborated evidence, not a ban on particular names or projection syntax. Independent guarantees from the acquisition callee remain available. Logical proof bindings and lemma calls may supply its certificate. If the loan already ended at return, that final value is the current value; otherwise the obligation may mention `final!(r)` and final values of returned reborrows only under `contracts.final.pending`. A loan retained through another parameter is tracked by the same borrow facts as a returned one; one runtime use does not imply that the loan ends at return. Access to the owner and proof fields is restored only after both preservation checking and loan end, even when the call returns without retaining any loan. The call is not awaited; deferred acquisition in a returned future or closure supplies no later opportunity to discharge the immediate obligation. Reborrows and swaps of a returned reference obey `runtime.borrows` and do not retarget the acquisition's final value.

r[contracts.invariants.acquisition-unwind]
A panic that unwinds out of an acquisition call aborts the process, whether or not the callee changed the lent field. Argument evaluation is outside this boundary: the arguments are evaluated once, in Rust's order, before the protected call. The protection covers unwinding from the call, including its cleanup, and ends on normal return; the preservation obligation is then discharged before the next runtime operation. A later caller panic unwinds normally with the affected owner valid when it can be observed or dropped. Lowering preserves this policy in both build programs and in export mode. A normal-return contract or an initialization precondition does not establish absence of panic. No no-unwind assumption is introduced.

r[contracts.invariants.assignment]
A field that a proof field reads is not assigned directly, and neither is a place inside it; nor is it initialized again after its value was moved out. Mutation through a loan admitted by `contracts.invariants.acquisition` is governed by that loan's preservation obligation. Otherwise it changes only when the whole value is replaced, by an assignment to the value or to something that contains it, or by taking the value apart and building it again, and either way every proof field is proved for the new value. A field that no proof field reads is assigned like any other, and a proof field that no other proof field reads may be assigned a value whose proofs prove its proposition.

r[contracts.invariants.proof-holders]
A field whose type holds a proof, such as an `Option<@P>`, counts as a proof field. A tuple component that a later component's proposition reads follows the rules for a field that a proof field reads.

r[contracts.unsafe-impls]
No `unsafe impl` that a derive or another macro generates is allowed on a type with proof fields. A hand-written `unsafe impl` is the programmer's promise, under [`logic.unsafe.invariant`](logical-layer.md#unverified-functions-and-unsafe-code), that the type's invariant is upheld.

r[contracts.invariants.observed]
A value of a type with proof fields satisfies them whenever the value or its proof fields can be observed. It is built with its proofs proved. During `contracts.invariants.acquisition` the affected owner and proof fields are suspended: no fact is obtained from the suspended proof fields, all affected propositions are proved at the loan's final value on normal return from acquisition, and the owner is available again only after both preservation checking and loan end. The acquisition unwind policy prevents observing or dropping that owner in a broken state. Outside this narrow exception, a field that a proof field reads changes only by replacement of the whole value. Code that Locus does not verify may hold, move, copy, or drop such a value, or call the type's own verified functions, but cannot build one or reach the fields that expose logical data or that its proofs read ([`logic.boundary.plain-data`](logical-layer.md#the-boundary-with-unverified-code)). So nothing observes such a value in a broken state: not a destructor, not code that catches a panic, and not another thread. Dropping a value takes it apart for the last time: its own destructor is given a value that satisfies its proof fields, and the destructors of its fields run afterwards.

r[contracts.slots]
`take_out` of Locus's library moves the value out of the target of a mutable reference and gives a slot for that place, and `put` on the slot writes a value there. From the one call to the other the place holds no value. After `put` it holds the value that `put` was given, as after an assignment. A panic that would unwind past a slot aborts the process, so nothing observes the place without a value.

r[contracts.slots.local]
A slot is bound to a local variable by the `let` whose initializer is the call of `take_out`. That variable is used only as the receiver of `put`: it is not moved, borrowed, assigned, captured, stored, or returned. Every path that leaves the variable's scope, other than by a panic, has passed it to `put`, and no `.await` lies between the two calls. Only a verified function calls `take_out`, whose result holds a proof.
