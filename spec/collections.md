# Locus's collections

Locus's library provides types of its own around the standard library's collections, which a program names with `use locus::std::…`. This chapter says what such a type is in the logic, what its methods state, and what a program still reaches of the standard library's type inside it. `Vec` is the one type written out. [RFC 0002](../design/rfcs/0002-logical-layer.md#assumptions-and-the-standard-library) explains the design.

In this chapter, for a method of `Vec<T>` that takes `self` by reference, `old` is `snap(self).elements()` and `new` is `snap(final!(self)).elements()`: the contents when the method is called, and when its borrow ends ([`contracts.final`](contracts.md#values-in-a-signature)). `s.push(e)` is the sequence `s` with `e` after its last element.

## Contents

r[collections.contents]
A collection type of Locus's library is a struct that holds the standard library's collection in one field and, in a logical field, the snapshots of the elements it holds, in order. Its snapshot is the struct's own, which the language supplies as it does for every struct ([`models.snapshots`](models.md#snapshots)): the standard library's collection is an opaque part, and the contents are the logical field's. No library declares it. Both fields are private to Locus's library, so a program reads neither ([`models.snapshot-privacy`](models.md#snapshots)), and reads the contents through an observer that the library gives the snapshot: for a `Vec<T>` whose `T` has a model, `snap(v).elements()` is a `Seq<Snap<T>>`, the elements' snapshots in order. The snapshot of a `Vec` is not itself a sequence, so `snap(v).len()` and `snap(v)[i]` are rejected. The logical field's type names `T` and asks nothing of it, so the struct has no `Model` bound, and `Vec<T>` is named, built, and moved at any `T`; it has a snapshot, and the observer, where `T` has a model ([`models.snapshots.seen`](models.md#snapshots)). The logical field is a field of the struct's own, so a collection type holds logical data, and at an element type that exposes none it is a sealed type ([`logic.boundary.logical-data`](logical-layer.md#the-boundary-with-unverified-code)).

r[collections.model]
The model of a `Vec<T>` of Locus's library is a `Seq` of its elements' models, in order. Locus's library declares it with the type, as a logic function of the snapshot, and Locus checks it as it checks a model that a program declares. `Vec::<T>::model_len(s)`, of Locus's library, is a lemma for a snapshot `s` of a `Vec<T>`: a proof of `Vec::<T>::model(s).len() == s.elements().len()`. A call names `T`, since a snapshot's type does not say which type it is a snapshot of. Neither a hole nor a procedure takes that step by itself ([`proofs.holes`](proofs.md#constructing-proofs)). So a proof about a vector read as a place, which is its model ([`models.observation`](models.md#models)), uses what a contract says of the elements' snapshots only where the lemma is called.

## The standard library's collection inside

r[collections.std-inside]
A collection type of Locus's library gives no mutable access to the standard library's collection inside it. It implements `Deref` to that type and not `DerefMut`, and no method of its own returns a mutable reference to it. So a method of the standard library's type that takes `&self` is reached through `Deref`, as the standard library's own function ([`logic.boundary.plain-data`](logical-layer.md#the-boundary-with-unverified-code)), and one that takes `&mut self` is not reached: a call of it is an error. The contents change only through the collection's own methods. `into_std(self)` gives the standard library's collection, and `from_std(plain)` builds Locus's from one. Neither states a contract: nothing is known of the contents of what `from_std` returns, their length included, until a method of the collection's own says it.

## The contracts of `Vec`

r[collections.vec.contracts]
The methods of Locus's `Vec<T>` that state a contract speak of the elements' snapshots ([`collections.contents`](#contents)), with `old` and `new` as this chapter defines them. `Vec::empty()` returns a vector `v` with a proof of `snap(v).elements().len() == 0`, and `Vec::new()` returns a vector alone, of whose contents nothing is known. `len(&self)` returns `n` with a proof of `n == old.len()`. `push(&mut self, x)` returns a proof of `new === old.push(snap(x)) && new.len() == old.len() + 1`. `pop(&mut self)` returns `last` with a proof of three things: `iff(snap(last) === None, old.len() == 0)`; `snap(last) === None ==> new === old`; and `forall |e: Snap<T>| snap(last) === Some(e) ==> (old === new.push(e) && old.len() == new.len() + 1)`. `get(&self, i, inside)` takes a proof `inside` of `i < old.len()`, and returns a reference `x` with a proof of `snap(x) === old.at(i, inside)`. `set(&mut self, i, x)` takes no proof and panics when `i` is outside the vector, and returns a proof of `i < old.len() && new === old.update(i, snap(x)) && new.len() == old.len()`. `clear(&mut self)` returns a proof of `new.len() == 0`. `view(&self)` returns the vector as a slice `items` with a proof of `snap(items) === old`. A method that returns `()` in the standard library returns its proof in that place, and one that returns a value returns the value and then the proof.

r[collections.vec.element-loan]
`get_mut(&mut self, i, inside)` of Locus's `Vec<T>` takes a proof `inside` of `i < old.len()`, and returns a mutable reference `x` to the element at `i`, with a proof of `snap(x) === old.at(i, inside)` and of `new === old.update(i, snap(final!(x))) && new.len() == old.len()`. The vector stays borrowed for as long as `x` is live ([`runtime.borrows`](runtime.md#writes-and-borrows)). When that borrow ends, the contents are the earlier ones with the value that the element ends with at `i` ([`contracts.final`](contracts.md#values-in-a-signature)).

r[collections.vec.indexing]
In runtime code, `v[i]` and `v[i] = x` on a `Vec` of Locus's library are `Index::index` and `IndexMut::index_mut`, which the library implements. A trait fixes the signatures of its methods, so neither states a contract ([`contracts.calls.unrelated`](contracts.md#calls)). `v[i]` gives an element of which nothing is known but its type: not that it is the element at `i` of the contents, and not that `i` was inside the vector, though the call panics when it is not. After `v[i] = x`, and after any other use of `&mut v[i]`, `v` has a new value of which nothing is known but its type: neither its contents nor their length. `get`, `set`, and `get_mut` give those facts. In logical code `v[i]` indexes the model of `v`, and calls neither.

## Element types

r[collections.element-types]
The methods of a collection of Locus's library that state a contract are declared for element types that have a model, `T: Model` ([`models.capture.bound`](models.md#models)). At an element type with none, such as a closure or a type of a crate that Locus does not lower, a call of one of them is rejected. It is never taken to be the standard library's method of the same name, also where rustc resolves the call to that method through `Deref`, as it can for a method that takes `&self`. A program that needs a collection of such elements uses the standard library's, as plain Rust, which logical code does not read ([`models.snapshots.seen`](models.md#snapshots)). The collection type itself asks nothing of its element type: at any `T` it is named, built with `new` and `from_std`, moved, and taken apart with `into_std`.
